# Slide 15 — B4 Failure Handling

### Recommended slide

```text id="a6t8n4"
              B4 FAILURE HANDLING

       Failure Type              Packet Loss

       Single link                 4 ms
       Encap switch               10 ms
       Transit switch           3300 ms
       OFC                          0 ms
       TE Server                    0 ms
       TE Disable/Enable            0 ms

                    ↓

        Most failures recover quickly

        BUT

        Transit-switch failure
        → ~3.3 seconds
        → major convergence bottleneck
```

These are the packet-loss measurements reported in the paper's failure experiments. 

---

# 1. First: What exactly are they measuring?

This is important.

The table is measuring:

> **Duration of packet loss after different failure events.**

It is **not** saying:

> "The system takes this long to detect every failure."

It is specifically about the observed **traffic loss time**.

That's a distinction worth remembering for Q&A.

---

# 2. Single link failure → 4 ms

Imagine:

```text id="gq5jkt"
A ───────── B
 \         /
  \       /
   ── C ─
```

Suppose one link breaks:

```text id="x1j8de"
A ────────X B
```

B4 switches can quickly remove the failed link from their ECMP groups.

So traffic loss was approximately:

### **4 milliseconds**

That's extremely short.

The paper attributes this to affected switches quickly pruning ECMP groups containing the failed link. 

---

# 3. Encapsulation switch failure → 10 ms

Now suppose the switch that starts the B4 tunnel fails.

Remember Slide 11:

```text id="fyvixs"
Source
(encapsulation)
     ↓
 Transit
     ↓
Destination
(decapsulation)
```

If the encapsulation switch fails, neighboring switches may need to perform multiple ECMP pruning operations.

That takes slightly longer.

Result:

### **10 ms packet loss**

Still relatively small.

---

# 4. Now the interesting one: Transit switch failure

This is the number I really want you to remember.

### **3,300 ms = 3.3 seconds**

Suppose:

```text id="r8m5ck"
A
 \
  B ← transit switch
 /
C
```

and B fails.

This can be much more expensive because multiple tunnels may have been passing through that transit switch.

The neighboring encapsulation switch may need to update its **multipath table entries** for those tunnels.

And the paper says these individual operations were typically slow—around **100 ms** at the time. 

So:

```text id="i4f3ku"
Transit switch failure
        ↓
Many tunnels affected
        ↓
Multipath table updates
        ↓
Slow switch operations
        ↓
~3.3 seconds packet loss
```

---

# 5. Why is this such an important result?

Because it exposes something deeper about B4.

The mathematical TE algorithm was fast.

We saw:

```text
TE computation
≈ 0.3 sec average
≈ 0.8 sec maximum
```

But now we see:

```text
Hardware/control operation
        ↓
Can take much longer
        ↓
3.3 sec in this failure case
```

So the paper is teaching us:

> **Optimizing the algorithm isn't enough. The network hardware and control path also determine real-world performance.**

That's a very good research lesson.

---

# 6. OFC failure → 0 ms

This one might initially seem strange.

Remember:

**OFC = OpenFlow Controller**

Its job is to maintain network state and instruct switches.

If the OFC fails, does the switch immediately stop forwarding packets?

### No.

The switch already has forwarding state installed.

Think:

```text id="6k2i2h"
          OFC
           │
     installs rules
           ↓
        SWITCH
           │
     forwarding tables
           ↓
         PACKETS
```

Once the switch has the forwarding rules, it can continue forwarding even if the controller temporarily disappears.

Therefore the measured packet loss for an OFC failure was:

### **0 ms**

The paper calls these failures **hitless**, meaning no data-plane traffic loss during failover, assuming no concurrent additional failures. 

---

# 7. TE Server failure → 0 ms

Same basic principle.

Remember:

```text
TE Server
    ↓
calculates desired network state
    ↓
SDN Gateway / OFC
    ↓
switch
    ↓
forwarding tables
```

The TE Server isn't sitting in the path of every packet.

It **controls the forwarding state**.

Therefore:

```text id="qceqby"
TE Server fails
      ↓
Existing switch rules remain
      ↓
Packets continue forwarding
```

Result:

### **0 ms packet loss**

Again, this assumes there aren't additional simultaneous failures.

---

# 8. What if Google disables TE completely?

This is another excellent design feature.

The paper reports:

### TE Disable/Enable → 0 ms packet loss

Why?

Because B4 has the fallback routing system.

We learned earlier:

```text id="bpy7y0"
BGP / IS-IS
      ↓
baseline routing
      ↓
normal forwarding
```

B4's TE rules have higher priority, but the baseline routing rules remain available.

So:

```text id="w8g3d0"
B4 TE
  ↓
something goes wrong
  ↓
Disable TE
  ↓
baseline routing
  ↓
traffic continues
```

This is the **"big red button"** idea we discussed earlier.

It gives operators a safety mechanism.

---

# 9. Very important distinction: TE failure vs data-plane failure

This is something you should understand deeply.

### TE server:

```text
Control plane
```

### Switch:

```text
Data plane
```

If the TE server fails:

```text
Control stops changing
       ↓
Existing forwarding state remains
       ↓
Packets can continue
```

But if an actual transit switch fails:

```text
Forwarding device fails
       ↓
Traffic path is affected
       ↓
Network must reconverge
       ↓
Potential packet loss
```

That's why:

**TE Server = 0 ms**

but

**Transit switch = 3.3 sec**

in the reported experiments.

---

# 10. The whole table in one picture

You can remember it like this:

```text id="j0h9l6"
                    FAILURE

                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓

   Link failure   Controller failure   Transit failure
       │               │                │
       ↓               ↓                ↓
      4 ms             0 ms            3.3 sec
                       │
                       ↓
              Existing forwarding
                 state survives
```

The surprising result is:

> **The most serious measured case wasn't the centralized TE server failing—it was a transit switch failure that required slow hardware-table updates.**

# Professor Q&A

### Q1. Which failure caused the largest packet loss?

**Answer:**

> A transit switch failure neighboring an encapsulation switch, causing about **3.3 seconds** of packet loss.

---

### Q2. Why was a single link failure only 4 ms?

> The affected switches quickly pruned ECMP groups containing the failed link.

---

### Q3. Why was transit-switch failure much slower?

> Multiple tunnels could have traversed the failed transit switch, requiring the neighboring encapsulation switch to update multipath table entries. Those switch operations were relatively slow.

---

### Q4. Why does TE server failure cause 0 ms packet loss?

> Because the TE server is part of the control plane. Existing forwarding state remains installed in the switches, so data-plane traffic can continue.

---

### Q5. What does "hitless" mean?

> The failure or restart of that software component does not cause data-plane traffic loss, assuming there are no concurrent additional failures.

---

### Q6. What happens if TE itself is disabled?

> Traffic falls back to the lower-priority forwarding rules established by the baseline routing protocol.

---

### Q7. Does 0 ms mean an OFC or TE server failure has no impact?

**Important answer:**

> No. It means the experiment observed no **data-plane packet loss** during that failure/failover. The control system is still affected, and future network changes may be impacted.

That's a much better answer than simply saying:

> "Nothing happens."
