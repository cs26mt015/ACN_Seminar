Now let’s understand **exactly what happens to a packet inside B4**. This is one of the most important parts for your seminar because it connects **TE + tunnels + OpenFlow + routing**.

## 1. The basic situation

Imagine three Google data centers:

```text
       Tunnel 1
DC A ───────────────► DC C
       \
        \ Tunnel 2
         ► DC B ─────► DC C
```

Suppose DC A wants to send a large amount of data to DC C.

B4 may decide:

```text
50% of traffic → Tunnel 1
50% of traffic → Tunnel 2
```

The source switch in DC A is responsible for splitting the traffic. The paper describes three switch roles:

1. **Encapsulating switch** — starts the tunnel and splits traffic.
2. **Transit switch** — forwards packets using the tunnel's outer header.
3. **Decapsulating switch** — ends the tunnel and returns the packet to normal routing. 

---

# 2. What does "encapsulation" mean?

Suppose the original packet looks conceptually like:

```text
[ Original IP Header ]
[ Original Data      ]
```

The source switch adds another IP header around it:

```text
[ Outer IP Header ]
[ Original IP Header ]
[ Original Data      ]
```

Think of it like putting a letter inside another envelope.

The **outer header tells the B4 network which tunnel the packet belongs to**.

Importantly, the outer destination IP is actually a **tunnel ID**, not necessarily the packet's real final destination. 

---

# 3. Why does B4 need this?

This is the clever part.

Suppose normal routing says:

```text
DC A ──► DC C
```

But B4's Traffic Engineering algorithm wants some traffic to take another path:

```text
DC A ──► DC B ──► DC C
```

Normal routing alone may not provide the desired traffic distribution.

So B4 essentially says:

> "I'll create tunnels representing the paths I want, and I'll tell the switches how to use them."

That's how B4 layers **Traffic Engineering on top of normal routing**. 

---

# 4. Follow one packet

Let's take this packet:

```text
Source:      DC A
Destination: DC C
```

B4 has two tunnels:

```text
Tunnel 1:
DC A ─────────► DC C

Tunnel 2:
DC A ──► DC B ──► DC C
```

The source switch hashes the packet header.

For example:

```text
Packet #1 → Tunnel 1
Packet #2 → Tunnel 2
Packet #3 → Tunnel 1
Packet #4 → Tunnel 2
```

The paper's example shows an encapsulating switch splitting flows across two paths using a hash of the packet header. 

---

# 5. Packet entering Tunnel 2

Suppose Packet #2 chooses:

```text
DC A → DC B → DC C
```

The source switch adds the tunnel's outer header:

```text
┌──────────────────────────┐
│ Outer Header             │
│ Tunnel ID                │
├──────────────────────────┤
│ Original IP Header       │
│ DC A → DC C              │
├──────────────────────────┤
│ Data                     │
└──────────────────────────┘
```

Now the packet enters the B4 network.

---

# 6. What does the transit switch see?

The transit switch doesn't need to understand the original application traffic.

It can simply look at the **outer header / tunnel ID**:

```text
Tunnel ID
    ↓
Forward according to tunnel
    ↓
Next site
```

So:

```text
DC A
 ↓
DC B
 ↓
DC C
```

The transit switch forwards according to the tunnel information configured by TE. 

This is an important concept for your seminar:

> **The tunnel gives B4 a way to control the path while the underlying network still performs ordinary packet forwarding.**

---

# 7. What happens at DC C?

When the packet reaches the destination site, the decapsulating switch recognizes the tunnel ID.

It removes the outer header:

```text
Before:

[ Outer Tunnel Header ]
[ Original Packet      ]


After:

[ Original Packet ]
```

Now the switch uses the **original packet's destination IP** and normal routing information to forward it toward the final destination.

The paper specifically says the destination switch uses **Longest Prefix Match (LPM) entries from BGP** after decapsulation. 

---

# 8. The whole journey

This is the picture I want you to remember:

```text
                 B4 Tunnel
        ┌────────────────────────┐
        │                        │
        ▼                        │
DC A ───────► DC B ───────────► DC C
 │             │                  │
 │             │                  │
 │ Encapsulate │ Transit          │ Decapsulate
 │             │                  │
 └─────────────┴──────────────────┘
                         ↓
                  Normal routing
                         ↓
                  Final destination
```

Or even simpler:

```text
SOURCE                 TRANSIT              DESTINATION
  DC A                    DC B                   DC C
   │                       │                      │
   │ Encapsulate           │ Forward              │ Decapsulate
   │                       │                      │
   └────── Tunnel ─────────┴──────────────────────┘
                                                  │
                                                  ▼
                                           Normal routing
```

---

# 9. Now connect this to OpenFlow

This is where your earlier concept of **SDN/OpenFlow** becomes useful.

B4's TE system decides:

```text
"Traffic should use these tunnels."
```

But the switch needs to actually implement that decision.

So B4 configures forwarding rules across the relevant switches.

The paper describes this as:

```text
TE decision
     ↓
OpenFlow state
     ↓
Hardware forwarding tables
     ↓
Actual packet forwarding
```

The source switch gets rules for **encapsulation**.

Transit switches get rules for **tunnel forwarding**.

Destination switches get rules for **decapsulation**. 

So remember:

> **TE decides what should happen; OpenFlow helps program the switches so that it actually happens.**

---

# 10. One more important idea: B4 doesn't throw away normal routing

This is a **very important seminar point**.

B4 has both:

```text
Normal routing
     +
Traffic Engineering
```

Normal routing uses the routing/BGP information.

TE adds more specific forwarding behavior.

The paper explains that B4 uses multiple forwarding tables in the switch hardware:

```text
              Incoming packet
                     │
             ┌───────┴────────┐
             ▼                ▼
        LPM table          ACL table
       (BGP routing)       (TE rules)
             │                │
             │          TE takes priority
             │                │
             └───────┬────────┘
                     ▼
              Desired forwarding
```

The **ACL rules take precedence over LPM entries**. The paper's example then uses a Multipath Table and hashing to distribute flows between tunnels. 

---

## 11. Why is that clever?

Imagine TE suddenly becomes unavailable.

B4 doesn't want the entire WAN to stop working.

Because normal routing is still there, B4 can disable TE and continue with shortest-path forwarding.

The paper explicitly describes this ability to operate with TE disabled. 

So the architecture is roughly:

```text
             B4 forwarding
                  │
        ┌─────────┴─────────┐
        │                   │
   Normal routing       B4 TE
    (BGP/LPM)         (ACL/tunnels)
        │                   │
        └─────────┬─────────┘
                  │
            Actual switch
             forwarding
```

### ⭐ Remember this for your seminar

**Routing answers:**

> "Where can the packet go?"

**TE answers:**

> "How should we distribute traffic across those possible paths?"

**OpenFlow answers:**

> "How do we program the switches to implement that decision?"

**Tunnel answers:**

> "How do we carry the packet along the TE-selected path?"

That's the complete connection.
