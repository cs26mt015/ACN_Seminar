Excellent. Now we reach one of the most important real-world parts of B4: **what happens when things fail?**

The paper is very explicit that B4 operates in a **distributed, failure-prone environment**. 

# 1. First understand the problem

Earlier we saw that a tunnel involves **multiple sites**.

For example:

```text
DC A ─────► DC B ─────► DC C
```

To create this tunnel, B4 has to configure switches at:

```text
DC A
DC B
DC C
```

So the central TE system can't simply say:

> "Create tunnel."

It has to make sure the necessary configuration reaches the appropriate sites.

This is where the **Traffic Engineering Database (TED)** comes in.

---

# 2. What is TED?

TED = **Traffic Engineering Database**.

Think of it as B4's record of:

```text
Which tunnels exist?
Which tunnel groups exist?
Which flow groups use them?
What configuration should each site have?
```

The TE server computes the desired configuration and converts it into **per-site TEDs**.

Then each Network Control Server / OpenFlow Controller uses its TED information to configure the switches at that site. 

Conceptually:

```text
              TE Server
                  │
          TE optimization
                  │
                  ▼
             Desired state
                  │
          ┌───────┴───────┐
          ▼               ▼
       TED Site A       TED Site B
          │               │
          ▼               ▼
        OFC A            OFC B
          │               │
          ▼               ▼
       Switches          Switches
```

---

# 3. Why doesn't the TE Server directly control every switch?

Because B4 wants to hide hardware-specific details from the central TE system.

The TE Server shouldn't need to worry about things like:

* exact switch hardware,
* hardware table management,
* hashing implementation,
* programming individual switches.

The OFC handles those details.

So:

```text
TE Server
   │
   │ "I want this forwarding state"
   ▼
OFC
   │
   │ translates it
   ▼
Switch hardware
```

The paper specifically describes this abstraction as insulating the TE Server from those lower-level issues. 

---

# 4. But there's a dangerous problem

Suppose B4 wants to create:

```text
Tunnel T1
Tunnel T2

      ↓
Tunnel Group TG1

      ↓
Flow Group FG1
```

You **cannot** necessarily install everything in any random order.

Imagine this happens:

```text
FG1 → TG1 → T1
```

but T1 hasn't been configured yet.

Then traffic may be directed toward something that doesn't exist.

That could cause packet drops.

So B4 has to respect **dependencies between operations**. 

---

# 5. The dependency rule

For example, when creating a tunnel:

```text
First:
Create/configure Tunnel

       ↓

Then:
Create Tunnel Group

       ↓

Then:
Create Flow Group
```

Conceptually:

```text
Tunnels
   ↓
Tunnel Group
   ↓
Flow Group
```

The paper gives exactly this kind of dependency: a tunnel must be configured at all affected sites before the corresponding TG and FG are configured. 

Similarly, if deleting a tunnel:

```text
Remove references to Tunnel
          ↓
Delete Tunnel
```

You shouldn't delete the tunnel while another configuration is still using it.

---

# 6. What is a TE operation?

B4 breaks configuration changes into small operations called **TE ops**.

One TE op can essentially change one TED entry at one OFC.

For example:

```text
TE Server
    │
    ├── TE op 1 → Site A
    ├── TE op 2 → Site B
    └── TE op 3 → Site C
```

The OFC converts those operations into actual switch-programming instructions.

It waits for acknowledgments (**ACKs**) from the devices before completing the operation. 

---

# 7. What if operations arrive in the wrong order?

This is a surprisingly important distributed-systems problem.

Imagine TE sends:

```text
Operation 1:
TG1 = T1:T2 = 50:50
```

Then a few milliseconds later:

```text
Operation 2:
TG2 = T1:T2 = 100:0
```

Why?

Because **T2 failed**.

So the desired state changed.

But networks aren't instantaneous.

It is possible that:

```text
Operation 2
   ↓
arrives first

Operation 1
   ↓
arrives later
```

Then the switch could accidentally apply the old state **after** the new state.

Bad.

---

# 8. B4 solves this with sequence IDs

B4 attaches a **site-specific sequence ID** to TE operations.

For example:

```text
Operation       Sequence ID

TG1 update          101
TG2 update          102
```

The OFC remembers the highest sequence ID it has processed.

If it receives:

```text
102 → accept
101 → reject
```

because 101 is older.

The TE Server can then retry the rejected operation. 

This is basically B4 saying:

> "Don't let an old configuration overwrite a newer configuration."

---

# 9. What if an operation fails?

Suppose TE sends:

```text
Configure Tunnel T1
```

But something goes wrong:

* RPC failure
* OFC rejects it
* hardware programming fails

Now B4 needs to remember:

> "The desired state says T1 should exist, but I'm not sure the switch actually has it."

B4 handles this using a **Dirty/Clean bit**.

### Clean

```text
Desired state = actual state
```

Everything is synchronized.

### Dirty

```text
Desired state ≠ confirmed actual state
```

Something may not have been successfully applied.

So:

```text
TE operation sent
       ↓
Mark entry DIRTY
       ↓
Wait for ACK
       ↓
ACK received?
   /          \
 YES          NO
  ↓            ↓
CLEAN       retry later
```

The dirty state persists across restarts, and B4 can replay the operation. The paper notes that TE operations are designed to be **idempotent**, making replay safe. 

---

# 10. What does "idempotent" mean?

This word is worth knowing for your seminar.

An operation is **idempotent** if doing it again doesn't cause an incorrect additional effect.

Simple example:

```text
Set Tunnel T1 = enabled
```

Doing:

```text
Set T1 = enabled
Set T1 = enabled
Set T1 = enabled
```

still leaves:

```text
T1 = enabled
```

So if B4 isn't sure whether an operation succeeded, it can safely replay it.

---

# 11. What if the TE controller itself has a problem?

B4 also has to handle failures of the control system.

The paper describes a **TE Session** between the master TE server and the master OFC.

They synchronize their TED views at the beginning of the session.

This also helps one side recover TED state from the other after a restart. B4 additionally synchronizes TED state to persistent storage to handle simultaneous failures. 

Conceptually:

```text
          TE Server
              │
        TE Session
              │
              ▼
             OFC
              │
       synchronized TED
```

---

# 12. What if the TE session can't be established?

This is another interesting case.

Suppose:

```text
TE Server
    X
   OFC
```

The control connection is unavailable.

Then TE may not know the current state of that site accurately.

B4's current design assumes the **last known state** and prevents new operations from being issued to that site. This is called **force fail** in the paper. 

That's safer than blindly sending new dependent changes when B4 doesn't know what state the site is actually in.

---

# 13. Put the whole failure mechanism together

This is the mental model I want you to remember:

```text
                    TE Server
                        │
                 computes desired
                     TE state
                        │
                        ▼
                       TED
                        │
                  TE operations
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
        OFC A                       OFC B
          │                           │
      sequence IDs               sequence IDs
      ACKs / retry               ACKs / retry
          │                           │
          ▼                           ▼
      Switches                    Switches
```

And underneath that:

```text
Dependencies
     ↓
Sequence IDs
     ↓
ACKs
     ↓
Dirty/Clean state
     ↓
Retry
     ↓
Persistent TED
     ↓
Recovery
```

### **"How does B4 handle failures?"**

> B4 maintains the desired Traffic Engineering state in TEDs and coordinates configuration across multiple sites using TE operations. ## One important distinction

Don't mix up these two kinds of failure:

**Data-plane failure**

```text
Link / switch / tunnel failure
        ↓
Traffic needs a new path
```

**Control-plane/software failure**

```text
TE server / OFC / RPC problem
        ↓
B4 must maintain or recover configuration state
```

The section we just studied is primarily about the **second problem**, while B4's traffic engineering and failure response also involve the first.
