# Slide 11 — How B4 Implements Tunnels

Now we move from **"what is a tunnel?"** to:

> **"How does an actual packet travel through that tunnel?"**

This is where **IP-in-IP encapsulation** becomes important.

The paper explicitly describes three switch roles: encapsulating, transit, and decapsulating switches. 

---

## 1. Slide title

### **How B4 Implements Tunnels**

Use this diagram:

```text id="4v5j1r"
                TUNNEL
        A ─────── B ─────── D
        │         │         │
        │         │         │
     SOURCE     TRANSIT   DESTINATION
   ENCAPSULATE   FORWARD   DECAPSULATE
```

Under it:

```text id="j5tqtu"
Original packet
      ↓
Add outer IP header
      ↓
Transit switches use outer header
      ↓
Destination removes outer header
      ↓
Original packet continues normally
```

---

# 2. What is IP-in-IP encapsulation?

Suppose the original packet is:

```text id="4h9kkl"
INNER PACKET

Source IP = A
Destination IP = D
```

B4 wants this packet to follow a particular tunnel:

```text id="t4j7aw"
A → B → D
```

At the source switch, B4 adds another IP header around the original packet.

Conceptually:

```text id="9g8tgn"
┌───────────────────────────────┐
│ OUTER IP HEADER               │
│ Source = tunnel source        │
│ Destination = tunnel ID       │
├───────────────────────────────┤
│ INNER IP PACKET               │
│ Source = A                    │
│ Destination = D               │
└───────────────────────────────┘
```

This is **IP-in-IP encapsulation**.

The paper says B4's source switches encapsulate packets with an outer IP header whose destination IP uniquely identifies the tunnel. 

---

# 3. Why add an outer header?

This is the key idea.

The **inner packet** says:

```text
A → D
```

But B4 wants the packet to follow a particular tunnel.

So it gives the packet an **outer identity** associated with that tunnel.

Think:

```text id="j3u8w4"
INNER:
"Where is the final destination?"

        ↓

OUTER:
"Which B4 tunnel should I follow?"
```

The paper specifically states that the outer destination IP acts as a **tunnel-ID rather than the actual destination**. 

---

# 4. What happens at each switch?

This is worth understanding very clearly.

## Step 1 — Source / Encapsulating switch

```text id="f5m4m6"
Original packet
      │
      ▼
Match Flow Group
      │
      ▼
Select Tunnel
      │
      ▼
Add outer IP header
```

The source switch:

* identifies the packet's Flow Group,
* uses the corresponding Tunnel Group,
* hashes the packet to a tunnel according to the desired ratio,
* encapsulates it.

The paper says incoming packets matching an FG are forwarded through its TG, and each incoming packet hashes to one of the associated tunnels in the desired ratio. 

---

# 5. Step 2 — Transit switch

The transit switch doesn't need to understand the original packet's final destination for this tunnel forwarding decision.

It looks at the **outer header**.

```text id="1x4cyr"
             PACKET
                │
                ▼
       Read outer header
                │
                ▼
        Identify tunnel-ID
                │
                ▼
       Forward to next hop
```

The paper explicitly says:

> transit switches forward packets based on the outer header. 

---

# 6. Step 3 — Destination / Decapsulating switch

When the packet reaches the destination site:

```text id="9f4hzi"
        Encapsulated packet
                │
                ▼
        Recognize tunnel-ID
                │
                ▼
          Remove outer header
                │
                ▼
         Original packet
                │
                ▼
       Normal IP forwarding
```

The destination switch removes the outer header.

Then it forwards the original packet using its normal routing information.

The paper specifically describes the destination switch as recognizing the tunnel ID, decapsulating, and then forwarding using regular routes/LPM. 

---

# 7. Complete packet journey

This is the diagram I recommend putting on the slide:

```text id="x8k3ts"
        SOURCE                TRANSIT             DESTINATION
          A                      B                     D
          │                      │                     │
          │  Encapsulate         │                     │
Packet ───┤                      │                     │
          │                      │                     │
          ├── Outer Header ────► │                     │
          │                      │                     │
          │                 Read outer                 │
          │                  header                    │
          │                      │                     │
          │                      ├────────────────────► │
          │                      │                      │
          │                      │               Decapsulate
          │                      │                      │
          │                      │                      ▼
          │                      │               Original packet
          │                      │                      │
          │                      │               Normal routing
```

You don't need to animate this. A clean static diagram is enough.

---

# 8. Very important: Tunnel ≠ physical cable

A professor might ask:

> "Is the tunnel an actual physical link?"

Answer:

> **"No. The tunnel is a logical site-level path. B4 implements it using IP-in-IP encapsulation and forwarding rules across the switches along that path."**

This distinction is very important.

For example:

```text id="9kn6zq"
Logical tunnel:

A ───── B ───── D

Physical network might actually be:

A ──┬── link 1 ──┬── B ──┬── link 1 ──┬── D
    ├── link 2 ──┤      ├── link 2 ──┤
    └── link 3 ──┘      └── link 3 ──┘
```

The TE system reasons at the site/tunnel level, while the underlying network handles the physical links.

---

# 9. What YOU say

Use this script:

> "B4 implements its tunnels using IP-in-IP encapsulation.
>
> At the source site, the switch identifies the Flow Group and selects one of the tunnels according to the Tunnel Group's configured weights. It then adds an outer IP header that identifies the tunnel.
>
> At transit sites, switches forward the packet based on this outer header.
>
> When the packet reaches the destination site, the destination switch recognizes the tunnel ID, removes the outer header, and then forwards the original packet using normal routing.
>
> So the outer header is used to carry the packet through the selected B4 tunnel, while the inner packet still contains the original source and destination information."

That is a very clear technical explanation.

---

# 10. Professor Q&A

### Q: Why use an outer IP header?

> "The outer header allows B4 to identify and forward the packet along the selected tunnel."

---

### Q: What does the outer destination IP represent?

> "It uniquely identifies the tunnel; the paper describes it as a tunnel-ID rather than the actual final destination."



---

### Q: Does the transit switch inspect the original destination?

For the tunnel-forwarding decision:

> "The transit switch forwards based on the outer header."



---

### Q: What happens at the destination?

> "The destination switch decapsulates the packet and then uses normal routing on the inner packet."



---

### Q: Who decides which tunnel the packet uses?

> "The TE system determines the Tunnel Group and its weights. The source switch then uses hashing to select one of those tunnels according to the desired ratio."

# Slide 12 — Integrating Routing with OpenFlow

This slide answers another very important question:

> **"If B4 already has BGP/IS-IS routing, how does TE actually coexist with it?"**

## Slide title

### **Integrating Routing with OpenFlow**

Use this simplified diagram:

```text id="j3q0f4"
       BGP / IS-IS
             │
             ▼
        Routing Stack
             │
             ▼
            RIB
             │
             ▼
            RAP
             │
       ┌─────┴─────┐
       │           │
   TE Match     No TE Match
       │           │
       ▼           ▼
  Multipath       LPM
       │
       ▼
    Tunnel
```

Then below:

```text id="m7d0ma"
TE Server
    ↓
SDN Gateway
    ↓
OFC
    ↓
OpenFlow
    ↓
Switch tables
```

---

# 1. The key idea

B4 has **two types of forwarding behavior**:

### Normal routing

```text
BGP / IS-IS
     ↓
LPM
     ↓
Normal forwarding
```

### TE forwarding

```text
TE
 ↓
ACL / Multipath
 ↓
Tunnel
 ↓
Forwarding
```

The paper explains that routing/BGP populates the LPM table, while TE uses the ACL table to establish its desired forwarding behavior. ACL rules take strict precedence over LPM entries. 

---

# 2. Why is this important?

Because B4 wanted:

> **TE when TE is available**

but also:

> **normal shortest-path routing when TE is disabled.**

So:

```text id="g1qbyx"
              Packet
                 │
        ┌────────┴────────┐
        │                 │
     TE rule?          No TE rule
        │                 │
       YES                NO
        │                 │
        ▼                 ▼
    Multipath             LPM
        │                 │
        ▼                 ▼
      Tunnel         Normal route
```

This is exactly what enables the **big red button** fallback we discussed earlier.

---

# 3. The roles of each component

Don't memorize the implementation details blindly. Understand the chain:

```text id="p1j9cv"
TE Server
   │
   │ decides desired TE state
   ▼
SDN Gateway
   │
   │ abstracts OpenFlow/hardware
   ▼
OFC
   │
   │ installs configuration
   ▼
OpenFlow
   │
   ▼
Switch
   │
   ▼
Forwarding tables
```

The paper describes the TE server outputting Tunnel Groups, Tunnels and Flow Groups to the SDN Gateway, which forwards them to OFCs, which install them using OpenFlow. 

---

# 4. The distinction you MUST remember

This is a very likely professor question:

### Who decides?

**TE Server**

### Who programs?

**OpenFlow / OFC**

### Who forwards packets?

**Switch hardware**

So:

```text id="1svf4h"
TE Server
   │
   │ "Use 60/40"
   ▼
OFC / OpenFlow
   │
   │ "Install these rules"
   ▼
Switch
   │
   │ "Actually forward packets"
   ▼
PACKETS
```

Don't say:

> "The TE server sends the packets."

It doesn't.

---

# 5. What YOU say

> "B4 also needed to integrate its new traffic-engineering system with existing routing.
>
> BGP and IS-IS continue to provide baseline routing information, which populates the normal LPM forwarding table.
>
> B4's TE system uses additional forwarding mechanisms to override the normal path when a packet matches a TE rule. The paper describes the ACL table taking precedence over the LPM table, allowing TE traffic to be directed through multipath and tunnel forwarding.
>
> This design allows B4 to support both TE and normal shortest-path routing. If TE is disabled, the normal routing system can continue forwarding traffic."

---

# 6. Professor Q&A

### Q: Why didn't B4 just replace BGP/IS-IS?

> "Because B4 wanted interoperability and a gradual path to introducing SDN. It therefore kept the existing routing system and layered TE on top."



---

### Q: What happens if there is no TE rule?

> "The packet can use the normal LPM-based routing behavior."



---

### Q: Which has priority: ACL or LPM?

> **"ACL rules take strict precedence over LPM entries."**



---

### Q: What does OpenFlow do here?

> "OpenFlow provides the mechanism for installing the TE forwarding state into the switches."

---

### Q: Does OpenFlow decide the optimal traffic allocation?

**No.**

> "The centralized TE service performs the traffic-engineering calculation. OpenFlow is used to install the resulting forwarding state."
