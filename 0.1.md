Great. Let’s continue with the **next prerequisite: Switch vs Router + what actually happens when a packet travels through a network**.

This is important because later, when we study B4, you’ll need to understand why Google could make the switches relatively simple and move more control into software.

## 1. Switch vs Router

Think of a network like a city.

* **Switch = connects places within the same local area**
* **Router = connects different networks/areas**

A simplified picture:

```text
                 Network A
        ┌─────────────────────────┐
        │                         │
     PC A ──┐                 ┌── PC B
            │                 │
            └─── [ SWITCH ] ──┘
                    │
                    │
                 [ ROUTER ]
                    │
                    │
        ┌───────────┴─────────────┐
        │                         │
     Network B                 Network C
```

### Switch

A switch primarily forwards traffic between devices connected to the same local network.

For example:

```text
PC A ──── Switch ──── PC B
```

PC A sends data → switch receives it → switch determines where to forward it.

The important concept is:

> **Switch forwarding is about getting a frame to the appropriate device/interface within the network.**

### Router

A router operates between IP networks.

```text
LAN A
  │
  │
Router
  │
  │
LAN B
```

The router looks at the destination IP and determines which network/path the packet should go toward.

So remember:

```text
SWITCH → forwarding inside a network
ROUTER → forwarding between networks
```

That's a simplified learning model; real networks can blur these boundaries because modern devices can perform both kinds of functions.

# 2. Now let's follow one packet

Suppose:

```text
Computer A
    │
    │
    ▼
 Switch
    │
    ▼
 Router
    │
    ▼
 WAN
    │
    ▼
 Router
    │
    ▼
 Switch
    │
    ▼
Computer B
```

Computer A wants to send data to Computer B.

Let's say:

```text
A = 10.1.1.10

B = 10.2.1.20
```

These are on different networks.

### Step 1 — Application creates data

For example, you open a website or transfer a file.

The application creates some data:

```text
"Hello"
```

That data doesn't simply travel as one giant object.

It goes through networking layers and eventually becomes packets/frames that can travel across the network.

For our current mental model:

```text
Application data
       ↓
     Packet
       ↓
     Frame
       ↓
   Physical transmission
```

Don't worry about all the OSI/TCP-IP details yet. We'll build those later if needed.

---

# 3. The first switch receives it

Computer A sends the Ethernet frame to the switch.

```text
PC A
 │
 │ frame
 ▼
SWITCH
```

The switch determines which interface the frame should be sent through.

For a beginner mental model:

```text
Incoming frame
      ↓
   SWITCH
      ↓
correct output port
```

The switch doesn't need to know the entire global Internet.

It mainly needs enough forwarding information to decide:

> "Which port should I send this frame out of?"

---

# 4. Then the router becomes important

Eventually the packet reaches a router.

```text
PC A
  ↓
Switch
  ↓
Router
```

The router examines the destination.

```text
Destination IP
      ↓
10.2.1.20
```

The router asks essentially:

> "Where should I send this packet next so that it gets closer to 10.2.1.20?"

This is where **routing** comes in.

---

# 5. Routing vs Forwarding

This distinction is extremely important for your B4 seminar.

### Routing

Routing is about **deciding paths**.

Imagine a map:

```text
        B
       /
A ---- C ---- D
       \
        E
```

There may be multiple possible paths:

```text
A → C → B
```

or

```text
A → C → D → B
```

Routing mechanisms determine which paths should be used.

### Forwarding

Forwarding is the actual action of sending the packet toward the selected next step.

So:

```text
ROUTING
"What path should traffic take?"

        ↓

FORWARDING
"Send this packet through this interface."
```

A useful way to remember it:

> **Routing makes the decision; forwarding carries out the decision.**

This distinction becomes very important in B4.

# 6. Why one path isn't always enough

Now imagine Google has:

```text
Data Center A
      │
      ├──────────── Path 1 ────────────┐
      │                                │
      └──────────── Path 2 ────────────┤
                                       │
                               Data Center B
```

Suppose:

```text
Path 1 = 100 Gbps
Path 2 = 100 Gbps
```

You have **200 Gbps total potential capacity**.

If everything is sent through Path 1:

```text
Path 1 ████████████████████ 100%
Path 2                     0%
```

you aren't using the available capacity efficiently.

Instead:

```text
Path 1 ██████████           50%
Path 2 ██████████           50%
```

could allow more traffic to move.

This is the basic intuition behind **traffic engineering**.

---

# 7. Traffic Engineering

Traffic Engineering, or **TE**, is about controlling how traffic uses the available network resources.

Very simplified:

```text
          Traffic
             │
             ▼
     ┌─────────────────┐
     │ Traffic         │
     │ Engineering     │
     └─────────────────┘
          │       │
          ▼       ▼
       Path 1   Path 2
          │       │
          └───┬───┘
              ▼
        Destination
```

Instead of simply asking:

> "What is the shortest path?"

TE can ask:

> "How should I distribute traffic across the available paths while considering capacity and competing demands?"

That distinction is **central to B4**.

The B4 paper explicitly describes its TE goal as sharing bandwidth among competing applications, potentially using multiple paths, with a **max-min fair allocation** objective. 

---

# 8. Why Google's network was interesting

Now we are getting very close to the actual B4 problem.

Google had data centers that needed to communicate with each other.

Examples from the paper include:

* asynchronous data copies
* index pushes
* data replication

The paper says well over 90% of internal application traffic runs over B4. 

So imagine:

```text
             Google B4 WAN

       Data Center A
             │
       ┌─────┴─────┐
       │           │
       ▼           ▼
     Path 1      Path 2
       │           │
       └─────┬─────┘
             │
       Data Center B
```

The amount of traffic can change.

At one moment:

```text
Application A → huge demand
Application B → small demand
```

Later:

```text
Application A → small demand
Application B → huge demand
```

And sometimes a link fails.

Therefore, Google wanted the network to **adapt how bandwidth was allocated**.

The paper describes B4 as having bandwidth-intensive applications whose traffic can adapt to available capacity, while Google also had control over the applications, servers, LANs, and network edge. 

---

# 9. Now we reach SDN

Here's the traditional idea:

```text
        Network
   ┌──────┼──────┐
   │      │      │
 Router Router Router
   │      │      │
   └──────┼──────┘

Each device has its own control logic.
```

SDN introduces a different idea:

```text
             CENTRAL
             CONTROL
                │
       ┌────────┼────────┐
       │        │        │
       ▼        ▼        ▼
    Switch   Switch    Switch
```

Instead of making every switch independently responsible for complex network-control decisions, some of the control can be centralized in software.

That's the fundamental intuition behind:

> **Software Defined Networking (SDN)**

And this is where B4 becomes particularly interesting.

The B4 paper says Google used SDN with **OpenFlow** to control relatively simple switches built from merchant silicon. 

---

# 10. Where OpenFlow fits

Think of the hierarchy like this:

```text
              SDN Controller
                    │
                    │ OpenFlow
                    ▼
              ┌───────────┐
              │  Switch   │
              └───────────┘
```

The controller can send instructions to the switch.

In B4 specifically, the switch contains an OpenFlow agent that receives OpenFlow commands from a remote OpenFlow Controller and translates them into driver commands used to configure forwarding-table entries. 

So:

```text
SDN
 │
 │ provides the overall architecture/idea
 ▼
Centralized software control
 │
 ▼
OpenFlow
 │
 │ communication/control mechanism
 ▼
Switch forwarding behavior
```
