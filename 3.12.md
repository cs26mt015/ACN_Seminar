# Slide 12 — OpenFlow + How B4 Programs the Switch

Now we connect **everything we've learned** to the actual switch.

We know:

* Routing tells B4 what paths exist.
* TE decides how traffic should be distributed.
* Tunnel Groups contain the traffic weights.
* OpenFlow is used to program the switches.
* Tunnels use encapsulation.

The important question is:

> **How does a packet get from the normal routing system into B4's TE forwarding behavior?**

The paper's answer is shown in its **"Integrating Routing with OpenFlow Control"** design. 

---

## 1. B4 did NOT throw away traditional routing

This is one of the most important things to understand.

B4 still uses:

```text
BGP
IS-IS
```

for traditional routing.

Conceptually:

```text
        BGP / IS-IS
             │
             ↓
        Routing Stack
             │
             ↓
            RIB
   (Routing Information Base)
```

The routing system continues to maintain normal network reachability.

Then B4 adds its TE mechanisms **on top of this**.

So don't say in your seminar:

> "B4 replaced routing with OpenFlow."

❌ That's incorrect.

Instead say:

> **"B4 retained traditional routing and layered centralized traffic engineering using OpenFlow."**

This is a very strong sentence for your presentation.

---

# 2. The B4 forwarding path

The paper's implementation has a component called **RAP** that bridges traditional routing and OpenFlow control. 

The simplified flow is:

```text
          BGP / IS-IS
               │
               ↓
        Routing / RIB
               │
               ↓
              RAP
               │
        ┌──────┴───────┐
        ↓              ↓
   Normal traffic   TE traffic
        │              │
        ↓              ↓
      LPM          Multipath
     lookup          table
                       │
                       ↓
                  Tunnel table
                       │
                       ↓
                    Output
```

Let's understand this carefully.

---

# 3. What happens to normal traffic?

Suppose a packet doesn't belong to B4's special TE traffic.

The switch can use normal routing.

The relevant concept is:

### **LPM — Longest Prefix Match**

For example:

```text
Destination:
10.20.30.40

Routing table:

10.20.0.0/16 → Port 1
10.20.30.0/24 → Port 2
10.20.30.40/32 → Port 3
```

The most specific matching prefix wins.

So:

```text
/32 beats /24
/24 beats /16
```

That is normal IP forwarding behavior.

You don't need to spend too much time on LPM in the seminar.

The important point is:

> **Normal traffic can continue using the normal routing path.**

---

# 4. What happens to B4 TE traffic?

Now suppose the packet matches a B4 TE rule.

The forwarding system can send it into the **multipath/TE processing**.

Conceptually:

```text
Packet
  │
  ↓
TE match?
  │
 ┌┴──────────────┐
 │               │
No              Yes
 │               │
 ↓               ↓
LPM          Multipath
                 │
                 ↓
             Tunnel(s)
```

The multipath table contains the information needed to distribute traffic across the selected tunnels according to their weights.

For example:

```text
Tunnel 1 → 30%
Tunnel 2 → 70%
```

The paper describes the ACL table as having precedence over the LPM table, allowing TE traffic to be identified and directed through the multipath processing. 

---

# 5. Why is the ACL important?

An **ACL**, or Access Control List, can identify packets based on matching conditions.

In B4's forwarding design, the ACL table has **strict precedence over LPM**.

So conceptually:

```text
              Incoming packet
                    │
                    ↓
                  ACL
                    │
          ┌─────────┴─────────┐
          │                   │
      TE match             No TE match
          │                   │
          ↓                   ↓
     Multipath                LPM
          │                   │
          ↓                   ↓
       Tunnel              Normal route
```

This allows B4 to say:

> "This particular traffic should use the centrally controlled TE path."

while other traffic can continue using normal routing.

---

# 6. Where does OpenFlow fit?

Now let's connect this to SDN.

The central TE system calculates the desired forwarding behavior.

Then:

```text
TE Server
    ↓
SDN Gateway
    ↓
OpenFlow Controller
    ↓
OpenFlow
    ↓
OpenFlow Agent
    ↓
Switch forwarding tables
```

The **OpenFlow Agent (OFA)** receives OpenFlow commands and translates them into commands understood by the switch's forwarding hardware/software.

So OpenFlow is basically the **programming interface between B4's control system and the switch forwarding behavior**. 

---

# 7. Very important distinction

You should now have this completely clear:

### TE Server

> **Decides what should happen.**

### OpenFlow

> **Provides a mechanism to program the switch.**

### Switch

> **Actually forwards packets.**

So:

```text
             DECISION
                ↓
          TE Server
                │
                ↓
          PROGRAMMING
                ↓
             OpenFlow
                │
                ↓
           FORWARDING
                ↓
             Switch
```

This distinction is excellent for Q&A.

---

# 8. Complete packet path

Let's combine everything.

Suppose:

```text
Server A → Server D
```

and B4 decides:

```text
A → B → D
```

The process is approximately:

```text
Application traffic
        │
        ↓
     Flow Group
        │
        ↓
   TE decision
        │
        ↓
   Tunnel Group
        │
        ↓
   OpenFlow rules
        │
        ↓
      Switch
        │
        ↓
   ACL / forwarding
        │
        ↓
   Multipath / tunnel
        │
        ↓
 IP-in-IP encapsulation
        │
        ↓
      Transit
        │
        ↓
    Decapsulation
        │
        ↓
   Destination
```

That's essentially the entire B4 mechanism we've been building piece by piece.

You can say:

>

>
> When a packet arrives, the forwarding system can identify TE traffic using the ACL mechanism. TE traffic is directed to the multipath processing and then to the appropriate tunnels. Traffic that doesn't match the TE rules can continue through normal longest-prefix routing.

# 🧠 Professor Q&A

### Q1. Does B4 replace BGP and IS-IS?

> **No.** B4 retains traditional routing and layers centralized traffic engineering on top of it.

---

### Q2. What is the purpose of OpenFlow?

> OpenFlow provides the mechanism through which the controller can program the switch's forwarding behavior.

---

### Q3. Does the TE Server forward packets?

> **No.** It calculates and distributes forwarding decisions. The switches forward the actual packets.

---

### Q4. Why does B4 need both LPM and multipath processing?

> LPM provides normal routing behavior, while multipath processing allows B4 to implement its TE decisions across multiple tunnels.

---

### Q5. Why does ACL have precedence?

> It allows the forwarding system to identify traffic that should receive TE treatment before falling back to normal LPM forwarding.

---

### Q6. What happens if TE fails?

This is a **very good question** because it leads directly into B4's reliability design.

B4 was designed with a fallback mechanism: operators could disable TE and return traffic to the normal shortest-path forwarding behavior—the paper describes this as a **"big red button."**

That means the centralized TE system wasn't supposed to be the only possible forwarding mechanism.

That's a much more accurate description of what Google actually built.
