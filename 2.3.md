# Figure 2 — How B4 combines Routing + OpenFlow

Now we get to one of the **most important technical parts of B4**.

You already understand:

> **Routing = decides the available paths.**
> **Traffic Engineering = decides how much traffic should use those paths.**
> **OpenFlow = programs the switches to implement the decision.**

Figure 4 in the paper shows **how B4 actually connects these pieces together**.

The figure is titled **“Integrating Routing with OpenFlow Control.”** 

---

# 1. First, forget the complicated boxes

Let's start with the big picture.

Imagine a packet:

```text
Application
    │
    ▼
Packet arrives at B4 switch
    │
    ▼
"Where should this packet go?"
    │
    ├── Normal routing information
    │       ↓
    │     BGP / IS-IS
    │
    └── TE information
            ↓
       OpenFlow rules
    │
    ▼
Final forwarding decision
    │
    ▼
Next hop / tunnel
```

The key idea is:

> **B4 uses traditional routing to understand the network, while OpenFlow adds the traffic-engineering behavior.**

---

# 2. Start with BGP / IS-IS

At the top of the Figure 4 diagram you saw:

```text
       BGP / IS-IS
            │
            ▼
           RIB
```

### What is RIB?

**RIB = Routing Information Base**

You can think of it as:

> **the router's collection of routing information.**

For example:

```text
Destination       Next hop
--------------------------------
1.2.3.0/24        interface 1
1.2.5.0/24        interface 2
```

BGP/IS-IS provide routing information, which eventually contributes to the routing state.

The important thing for B4 is that it **doesn't throw away this existing routing system**.

---

# 3. Then comes Quagga

In the paper's implementation, B4 used **Quagga** for the traditional routing stack.

Think of it as:

```text
BGP / IS-IS
     │
     ▼
  Quagga
     │
     ▼
    RIB
```

So Quagga is handling the conventional routing side.

Then B4 adds its own control mechanisms around it.

---

# 4. Now the interesting part — RAP

Figure 4 contains something called **RAP**.

Don't worry about memorizing the acronym yet.

Conceptually, RAP acts as a bridge between:

```text
Traditional routing
        │
        ▼
       RIB
        │
        ▼
      RAP
        │
        ▼
 OpenFlow control
```

Why is this necessary?

Because the routing system thinks in terms of:

> "For this destination prefix, this is the normal next hop."

But B4's TE system wants to say:

> "Actually, this traffic belongs to a particular Flow Group, and I want to distribute it across these tunnels."

So B4 needs a mechanism to combine the two.

---

# 5. Here comes the ACL table

This is where it becomes much more interesting.

The paper describes two forwarding mechanisms:

```text
             Incoming packet
                    │
                    ▼
              ┌───────────┐
              │ ACL table │
              └─────┬─────┘
                    │
              TE rule matches?
              /             \
            YES              NO
             │                │
             ▼                ▼
       TE / multipath       Normal
          processing       routing
                              │
                              ▼
                         LPM table
```

### LPM

**LPM = Longest Prefix Match**

This is the normal IP routing mechanism.

For example:

```text
Packet destination:
9.0.0.1

Routing table:

9.0.0.0/24 → port 3
9.0.0.1/32 → port 5
```

The more specific prefix wins.

That's the basic idea of longest-prefix matching.

---

# 6. Why does B4 put ACL before normal routing?

This is a **very important concept**.

Suppose a packet arrives:

```text
Destination = 9.0.0.1
```

Normal routing might say:

```text
9.0.0.0/24 → port 3
```

But B4's TE system may say:

> "Wait. This traffic belongs to a Flow Group that I want to distribute across two tunnels."

Therefore:

```text
Packet
  │
  ▼
ACL
  │
  ├── matches TE rule → use TE
  │
  └── no match → normal routing
```

The paper states that the ACL table has **strict precedence over the LPM table**. 

This is essentially how B4 can say:

> **"For this particular traffic, override normal routing and apply TE."**

---

# 7. What happens after an ACL match?

Now we get to the **Multipath Table**.

Imagine:

```text
                Packet
                   │
                   ▼
              ACL Table
                   │
                   ▼
            Multipath Table
               /        \
              /          \
        Tunnel 1       Tunnel 2
           40%            60%
```

Suppose B4 wants:

```text
Tunnel 1 → 40%
Tunnel 2 → 60%
```

The Multipath Table helps implement that distribution.

The paper explains that matching packets can be hashed to the tunnels associated with the corresponding Tunnel Group according to the desired ratio. 

---

# 8. Why hashing?

You might ask:

> "Why doesn't B4 simply send every second packet down another tunnel?"

Because that could cause packet reordering.

Instead, B4 uses hashing so that traffic can be distributed consistently.

Conceptually:

```text
Flow A ──hash──→ Tunnel 1
Flow B ──hash──→ Tunnel 2
Flow C ──hash──→ Tunnel 2
Flow D ──hash──→ Tunnel 1
```

The exact implementation is more detailed, but your seminar-level understanding should be:

> **Hashing distributes traffic among the selected tunnels according to the desired traffic split.**

---

# 9. Now: what is an Encapsulation Tunnel?

This is the next crucial part.

Suppose the selected path is:

```text
A → C → B
```

B4 represents this as a **tunnel**.

At the source switch, B4 adds an **outer IP header**.

Think:

```text
Original packet

┌────────────────────────────┐
│ Original IP header         │
│ Original payload           │
└────────────────────────────┘
```

becomes:

```text
┌────────────────────────────┐
│ OUTER IP HEADER            │ ← tunnel information
├────────────────────────────┤
│ Original IP header         │
├────────────────────────────┤
│ Original payload           │
└────────────────────────────┘
```

This is IP-in-IP style encapsulation.

The paper explains that the outer destination identifies the tunnel rather than the final application destination. 

---

# 10. Why do this?

Because the intermediate switches need to know:

> **"Which B4 tunnel should I forward this packet along?"**

They don't need to understand the entire original application flow.

They can simply forward based on the tunnel information.

So:

```text
Source switch
     │
     │ add tunnel header
     ▼
Transit switch
     │
     │ look at tunnel ID
     ▼
Transit switch
     │
     ▼
Destination switch
     │
     │ remove tunnel header
     ▼
Normal forwarding
```

This is a very elegant idea.

---

# 11. Three switch roles

You should absolutely know these three.

### ① Encapsulating switch

At the beginning:

```text
Original packet
      ↓
Add outer tunnel header
      ↓
Send into tunnel
```

### ② Transit switch

In the middle:

```text
Look at outer/tunnel information
          ↓
Forward packet
```

### ③ Decapsulating switch

At the destination:

```text
Remove outer tunnel header
          ↓
Recover original packet
          ↓
Normal IP forwarding
```

The paper explicitly describes these three roles. 

---

Now look at the entire process:

```text

                          ▼
                    Routing state
                          │
                          │
Packet ───────────────► B4 switch
```

**This is one of the most important diagrams for your entire seminar.**

# 13. The beautiful part: routing + TE coexist

This is the thing I want you to understand deeply.

B4 isn't saying:

> "Traditional routing is useless."

Instead:

```text
             Traditional routing
                    +
          Traffic Engineering
                    ↓
              B4 forwarding
```

Normal routing provides the baseline.

TE can override the forwarding behavior for traffic that needs engineering.

If TE doesn't apply:

```text
Packet → LPM → normal route
```

If TE applies:

```text
Packet → ACL → Multipath → Tunnel
```

And that's why the architecture is powerful.

---

# 14. Professor question: "Why not just change the routing table?"

This is an excellent possible question.

### Weak answer:

> "Because B4 uses OpenFlow."

That's technically related but doesn't explain **why**.

### Strong answer:

> "B4 needs more control than simply choosing one routing-table next hop. Traffic engineering may need to distribute a Flow Group across multiple tunnels with specific ratios. Therefore B4 uses OpenFlow-based forwarding structures such as ACL and multipath tables to implement those TE decisions while retaining the existing routing system."

That's the kind of answer that gets you beyond memorization.

---

# 15. Professor question: "What happens if there is no TE rule?"

Answer:

> "The packet falls back to normal routing through the LPM table."

This is important because B4's TE system is **layered on top of** normal routing rather than replacing it. 

---

# 16. Professor question: "What is the difference between a tunnel and a path?"

This can be tricky.

For B4:

**Path** is the conceptual sequence of sites:

```text
A → C → B
```

**Tunnel** is B4's mechanism for carrying traffic along that site-level path, using encapsulation and tunnel identifiers.

The paper describes a tunnel as a site-level path and says B4 implements tunnels using IP-in-IP encapsulation. 

---

# 17. Don't confuse these four things

This distinction will save you during Q&A:

| Concept      | Question it answers                             |
| ------------ | ----------------------------------------------- |
| **Routing**  | Where can traffic go?                           |
| **TE**       | How should traffic be distributed?              |
| **Tunnel**   | How do we represent/carry the selected path?    |
| **OpenFlow** | How do we program the switches to implement it? |

And then:

| Mechanism           | Purpose                                         |
| ------------------- | ----------------------------------------------- |
| **LPM**             | Normal IP forwarding                            |
| **ACL**             | Identify traffic requiring special TE treatment |
| **Multipath Table** | Select/distribute traffic across tunnels        |
| **Hashing**         | Distribute flows according to the desired split |
| **Encapsulation**   | Carry traffic through the selected tunnel       |

If you understand this table, you're doing very well.

---

# 18. Your 30-second explanation

If the professor points at Figure 4 and says:

> **"Explain this."**

You should be able to say:

> "B4 integrates traditional routing with OpenFlow-based traffic engineering. BGP and IS-IS provide the normal routing information through the routing stack. For packets that match a B4 traffic-engineering rule, the ACL table takes precedence over normal LPM forwarding. The packet is then mapped to a multipath group, where hashing distributes traffic among selected tunnels according to their configured weights. At the source, the packet is encapsulated with tunnel information, transit switches forward it based on that information, and the destination switch decapsulates it and resumes normal forwarding."

That's a **seminar-quality explanation**.
