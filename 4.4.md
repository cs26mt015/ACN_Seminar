# 1. What does "16 sites" mean?

Think of a simplified version:

```text
       Data Center A
             |
             |
       Data Center B
        /          \
       /            \
Data Center C ---- Data Center D
```

Each **site** represents a Google data-center location in the B4 WAN.

During the reported deployment period, B4 had:

**16 sites.**

Don't say:

> "B4 had only 16 routers."

That's wrong.

A site is a logical network location/data-center site containing networking equipment.

---

# 2. What are the 46 unidirectional edges?

Remember our earlier concept:

> **Logical edge = connectivity between two sites.**

The paper represents the topology at the **site level**.

For example:

```text
A ─────→ B
```

is one directed edge.

And:

```text
B ─────→ A
```

is another directed edge.

So when the paper says:

**46 unidirectional edges**

it is talking about the site-level topology representation, not simply saying there were 46 physical cables.

This is a good example of why we learned the **logical topology** concept earlier.

---

# 3. 2,700 Flow Groups

Remember:

```text
Flow Group = {source site, destination site, QoS}
```

Why not let the TE system calculate a path separately for every individual application flow?

Because that wouldn't scale well.

Instead, B4 groups traffic.

So:

```text
Applications
     ↓
Flow Groups
     ↓
Traffic Engineering
```

The production deployment had approximately:

**2,700 Flow Groups.**

That tells us the TE system was handling a significant amount of traffic-management state.

---

# 4. 240 Tunnel Groups

We learned:

```text
Flow Group
     ↓
Tunnel Group
     ↓
Multiple tunnels + weights
```

For example:

```text
FG: A → D

       ┌── T1: A → B → D : 60%
FG ────┤
       └── T2: A → C → D : 40%
```

The production system had:

**240 Tunnel Groups.**

Notice that the numbers don't have to be equal:

```text
2700 Flow Groups
240 Tunnel Groups
```

because these are **different abstractions**.

A professor could easily ask:

> "What's the difference between an FG and a TG?"

Answer:

> **A Flow Group identifies the traffic being managed, while a Tunnel Group specifies which tunnels carry that traffic and in what proportions.**

That's a very good viva answer.

---

# 5. 350 tunnels in use

The paper reports approximately:

**350 tunnels in use**

and

**1,150 cached tunnels.**

Don't confuse these.

Think:

```text
             B4 tunnel state

       Currently being used
              ↓
          350 tunnels

       Already cached/available
              ↓
         1,150 tunnels
```

You don't necessarily need to put **1,150** on the main slide.

Mention it only if you want to demonstrate deeper knowledge during Q&A.

---

# 6. Why do "topology changes per day" matter?

The paper reports approximately:

**286 topology changes per day.**

And approximately:

**7 edge additions/deletions per day.**

This is useful because it shows the network wasn't static.

The system had to deal with changes like:

```text
Normal operation
      ↓
Topology changes
      ↓
Network state changes
      ↓
TE needs updated information
      ↓
New forwarding state may need to be installed
```

So B4 wasn't just:

> "Calculate a path once and leave it forever."

It had to operate continuously.

---

# 7. Why 5 TE servers?

This is an important architecture point.

B4 had:

**5 geographically distributed TE servers.**

Why multiple servers?

Because putting the entire TE service on one machine would create a dangerous single point of failure.

Conceptually:

```text
        TE Server 1
        TE Server 2
        TE Server 3
        TE Server 4
        TE Server 5
             ↓
      logically centralized
             ↓
          B4 WAN
```

Remember our earlier distinction:

### Logically centralized ≠ physically one machine.

There can be multiple replicated servers while the system behaves like one centralized TE service.

---

# 8. What happens if the primary TE server fails?

B4 used **hot standbys**.

The paper reports that a standby could take over in:

**less than 10 seconds.**

So:

```text
Primary TE Server
       ❌
       ↓
Hot Standby
       ↓
Becomes primary
```

This is important because it shows that B4's designers understood:

> **Centralization improves global control, but the centralized control system itself must be fault tolerant.**

That's a great seminar point.

---

# 9. The TE algorithm was actually fast

This is one of the most interesting numbers.

The paper reports roughly:

* **540 TE runs/day**
* **0.3 seconds average**
* **0.8 seconds maximum**

So the mathematical TE computation itself was quite fast.

You can say:

> "The optimization algorithm was not the major problem. It could run hundreds of times per day and typically completed in a fraction of a second."

This connects directly to the algorithm we studied earlier.

Remember:

```text
Network state
     ↓
TE Optimization
     ↓
Tunnel Groups
     ↓
OpenFlow
     ↓
Switches
```

The **optimization calculation** was fast.

But the later part—

```text
OpenFlow
   ↓
Switch
   ↓
Hardware programming
```

—could introduce substantial latency.

The paper explicitly discusses switch programming as a significant operational bottleneck.

# Professor Q&A you should prepare

### Q1. Was B4 only a simulation?

**Answer:**

> No. B4 was a real production WAN deployed by Google, and the paper reports operational experience and measurements from that deployment.

---

### Q2. Why did B4 need multiple TE servers?

> For fault tolerance and availability. The service was logically centralized but replicated across geographically distributed servers.

---

### Q3. If the TE algorithm takes only 0.3 seconds, what was the bottleneck?

> Programming the network hardware and the control path could introduce significant latency. The optimization computation itself was relatively fast.

---

### Q4. Why is 2,700 Flow Groups important?

> It demonstrates that B4 was managing traffic at a substantial production scale rather than just a small experimental network.

---

### Q5. What is the difference between 350 tunnels in use and 1,150 cached tunnels?

> 350 were actively in use, while 1,150 were cached tunnel state. They represent different operational states of tunnel information.

---

### Q6. Is B4 centralized on one physical server?

> No. B4's TE service is **logically centralized** but implemented using replicated servers for fault tolerance.
