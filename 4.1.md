---

# 2. Understand the difference

This is something your professor can easily ask.

### Routing

Routing answers:

> **"What path can packets take?"**

For example:

```text
A → B → D
A → C → D
```

The routing system determines reachable paths.

---

### Traffic Engineering

TE asks:

> **"How should I distribute traffic across those available paths?"**

For example:

```text
A → B → D = 60%
A → C → D = 40%
```

So:

```text id="9b0t3d"
ROUTING
   ↓
Available paths

        +

TRAFFIC ENGINEERING
   ↓
Traffic distribution
```

This distinction is **fundamental to B4**.

---

# 3. Why didn't B4 simply replace routing?

This is where B4 becomes clever.

The authors considered an approach where routing and TE could be integrated into one centralized service.

Instead, they chose:

```text id="m7x2hx"
        Existing Routing
          BGP / IS-IS
               │
               ▼
        Baseline routing
               │
               +
               │
               ▼
      Centralized Traffic
         Engineering
               │
               ▼
          OpenFlow
```

Why?

The paper gives several reasons, including allowing gradual deployment and giving the team time to develop and debug the SDN infrastructure before introducing new functionality such as TE. 

---

# 4. The "Big Red Button"

This is a **great detail to mention in your seminar**.

B4 layered TE on top of baseline routing using prioritized forwarding entries.

That gave the system a fallback:

```text id="m9i1x7"
             B4
              │
        ┌─────┴─────┐
        │            │
      TE ON        TE OFF
        │            │
        ▼            ▼
 Centralized      Shortest-path
 traffic           forwarding
 engineering
```

The paper calls this a **"big red button"** because operators could disable TE and fall back to shortest-path forwarding if there were critical TE problems. The paper says this fault-recovery mechanism proved invaluable. 

This connects directly to the outage slide we studied earlier.

---

# 5. Site-level topology abstraction

There is another important technical idea.

A B4 site could contain **multiple switches and many physical links**.

Instead of making the centralized TE system reason about every physical link individually, B4 abstracts:

```text id="8d0y7s"
Physical network:

       ┌── Link ──┐
Site A ├── Link ──┼── Site B
       ├── Link ──┤
       └── Link ──┘
```

into something like:

```text id="7m8qgm"
       Site A ═════════ Site B
              capacity
```

So the TE system sees:

> **Site = logical node**

and

> **Site-to-site connectivity = logical edge**

The physical links underneath are handled using B4's custom ECMP hashing. 

---

# 6. What YOU say during the presentation

Here's a good script:

> "Before discussing B4's traffic engineering, we need to distinguish routing from traffic engineering.
>
> Routing determines which paths are available between sites. For example, traffic from A to D may have a path through B and another through C.
>
> Traffic engineering then decides how much traffic should use each available path. For example, B4 could allocate 60 percent to one path and 40 percent to another.
>
> B4 did not replace its existing routing protocols. Instead, it kept BGP and IS-IS as the baseline routing system and layered centralized traffic engineering on top.
>
> This also provided an important safety mechanism. If there was a problem with traffic engineering, operators could disable TE and fall back to shortest-path forwarding.
>
> Finally, B4 abstracted each site as a logical node and site-to-site connectivity as a logical edge, while distributing traffic across the physical links underneath."

That's a **very strong explanation** for this slide.

# 7. Professor Q&A

### Q: What is the difference between routing and traffic engineering?

**Answer:**

> "Routing determines the available paths, while traffic engineering determines how traffic should be distributed across those paths."

### Q: Did B4 replace BGP and IS-IS?

**Answer:**

> "No. B4 retained them as baseline routing protocols and layered centralized traffic engineering on top."



---

### Q: Why keep the existing routing protocols?

**Answer:**

> "It supported interoperability and provided a gradual path for introducing SDN into the existing production network."



---

### Q: What happens if B4's TE system has a serious problem?

**Answer:**

> "Operators can disable TE and fall back to shortest-path forwarding. The paper describes this as a 'big red button' and says it proved valuable for fault recovery."



---

### Q: Is the logical edge the same thing as one physical cable?

**Answer:**

> "No. A logical site-to-site edge can represent multiple physical links. B4 uses custom ECMP hashing to distribute traffic across those constituent links."

# Slide 8 — Flow Groups → Tunnels → Tunnel Groups

Now we're getting into the **core mechanism B4 uses to actually represent and distribute traffic**.

## Slide title

### **Flow Groups → Tunnels → Tunnel Groups**

Put these three concepts horizontally:

```text id="m8o4o8"
┌────────────────┐
│  FLOW GROUP    │
│                │
│ WHAT traffic?  │
└───────┬────────┘
        │
        ▼
┌────────────────┐
│    TUNNEL      │
│                │
│ WHICH path?    │
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ TUNNEL GROUP   │
│                │
│ HOW MUCH on    │
│ each path?     │
└────────────────┘
```

This is one of the **best diagrams in your entire presentation** because it gives the audience a simple mental model.

---

## 1. Flow Group — What traffic?

A **Flow Group (FG)** is defined by:

```text
{source site,
 destination site,
 QoS}
```

So you can think:

```text
FG =
Google Site A
      →
Google Site D
      +
QoS requirement
```

Instead of treating every individual packet or flow as a completely separate TE object, B4 groups traffic using these attributes.

---

## 2. Tunnel — Which path?

Suppose:

```text
A ── B ── D
```

That's one tunnel.

Another could be:

```text
A ── C ── D
```

So:

```text
Tunnel 1 = A → B → D

Tunnel 2 = A → C → D
```

The tunnel represents a **site-level path**.

It is implemented using **IP-in-IP encapsulation**, which we'll explain in detail on Slide 11.

---

## 3. Tunnel Group — How much?

Now suppose our Flow Group is:

```text
FG: A → D
```

and there are two tunnels:

```text
T1: A → B → D
T2: A → C → D
```

B4 can create a Tunnel Group:

```text
TG
├── T1 → 60%
└── T2 → 40%
```

So:

```text
Flow Group
    │
    ▼
Tunnel Group
   /    \
 60%    40%
 /        \
T1         T2
```

---

# 4. The easiest way to remember it

Memorize this:

> **Flow Group = WHAT traffic?**

> **Tunnel = WHICH path?**

> **Tunnel Group = HOW MUCH traffic on each path?**

If the professor asks you to explain B4's TE representation, this three-line answer is excellent.

---

# 5. What YOU say

> "B4 represents traffic engineering using three important concepts: Flow Groups, Tunnels and Tunnel Groups.
>
> A Flow Group identifies traffic using its source site, destination site and QoS.
>
> A Tunnel represents a path through the WAN, such as A to B to D.
>
> Finally, a Tunnel Group associates a Flow Group with one or more tunnels and assigns weights to them. These weights determine the fraction of traffic sent over each tunnel.
>
> So, in simple terms: the Flow Group tells us what traffic we are talking about, the Tunnel tells us which path it can use, and the Tunnel Group tells us how much traffic should use each path."

---

# 6. Professor Q&A

### Q: Why use Flow Groups?

> "They provide an aggregate representation of traffic for traffic engineering instead of requiring the TE system to reason about every individual packet."

Be careful: keep the answer at this level unless the professor asks for more implementation detail.

---

### Q: What does the weight in a Tunnel Group mean?

> "It represents the fraction of the Flow Group's traffic that should be sent through that tunnel."

---

### Q: Is a tunnel a physical cable?

**No.**

> "No. A tunnel is a logical path through the WAN. B4 implements it using IP-in-IP encapsulation."

---

### Q: Can one Flow Group use multiple tunnels?

**Yes.**

That's actually the whole point of the Tunnel Group.

Example:

```text
FG
│
├── T1 → 60%
│
└── T2 → 40%
```
