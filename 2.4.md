# Figure 3 — B4 Traffic Engineering Algorithm

Now we reach the **heart of B4**.

So far, we know:

```text
Routing
   ↓
Possible paths/tunnels
   ↓
Traffic Engineering
   ↓
???
```

The big question is:

> **How does B4 decide exactly how much traffic should go through each tunnel?**

For example:

```text
Tunnel 1 → 30%
Tunnel 2 → 70%
```

or:

```text
Tunnel 1 → 50%
Tunnel 2 → 40%
Tunnel 3 → 10%
```

The B4 paper's TE algorithm is responsible for calculating these allocations. The paper describes its objective as a **max-min fair allocation** while maintaining high network utilization. 

---

# 1. First: what is B4 trying to optimize?

Imagine three applications are competing for the same network:

```text
Application A ──┐
Application B ──┼──► Limited network bandwidth
Application C ──┘
```

Suppose the network has:

```text
100 Gbps
```

but the applications collectively want:

```text
150 Gbps
```

We can't give everybody everything.

So B4 needs to decide:

> **Who gets how much bandwidth?**

And it wants the allocation to be **fair**.

---

# 2. What does "max-min fair" mean?

Don't let the mathematical name scare you.

The basic idea is:

> **Give resources fairly, while trying to maximize the allocation of the applications that are currently getting less.**

Simple example:

Suppose:

```text
App A wants 80 Gbps
App B wants 20 Gbps
App C wants 20 Gbps
```

and we have:

```text
100 Gbps total
```

A reasonable allocation could be:

```text
A → 60
B → 20
C → 20
```

B and C get everything they need, and the remaining capacity goes to A.

The exact B4 algorithm is more sophisticated, but **fairness under capacity constraints** is the key concept.

---

# 3. B4 doesn't optimize individual applications directly

This is an important design decision.

Imagine Google has:

```text
Thousands of applications
```

It would be difficult to calculate TE independently for every individual application.

So B4 introduces a concept called a:

## Flow Group (FG)

A Flow Group is identified by:

```text
{Source site, Destination site, QoS}
```

So instead of thinking:

```text
Application 1
Application 2
Application 3
Application 4
...
```

B4 can group traffic into manageable Flow Groups.

The paper explicitly defines an FG using source, destination, and QoS. 

---

# 4. Then B4 gives each Flow Group some tunnels

Suppose:

```text
FG1 = Site A → Site B
```

and there are three possible tunnels:

```text
Tunnel 1: A → B
Tunnel 2: A → C → B
Tunnel 3: A → D → B
```

So:

```text
             ┌── Tunnel 1 ──────── B
             │
A ───────────┼── Tunnel 2 ─ C ─── B
             │
             └── Tunnel 3 ─ D ─── B
```

B4 now needs to determine:

```text
Tunnel 1 → ?
Tunnel 2 → ?
Tunnel 3 → ?
```

That allocation is represented using a:

## Tunnel Group (TG)

A Tunnel Group maps a Flow Group to a set of tunnels and their weights.

The weight represents the fraction of traffic sent through each tunnel. 

---

# 5. Here's where the algorithm starts

The paper's TE optimization algorithm has two major parts:

```text
       TE Optimization Algorithm
                  │
        ┌─────────┴─────────┐
        │                   │
        ▼                   ▼
Tunnel Group             Tunnel Group
Generation               Quantization
        │                   │
        ▼                   ▼
 Ideal allocation      Hardware-friendly
                       allocation
```

The first part figures out the **ideal traffic split**.

The second part converts that split into something the switch hardware can actually implement. 

---

# 6. Tunnel Group Generation

Let's use a simplified example.

Suppose:

```text
FG1
```

has:

```text
Demand = 20 Gbps
```

and two tunnels:

```text
T1 = A → B
T2 = A → C → B
```

Imagine:

```text
T1 capacity = 10 Gbps
T2 capacity = 30 Gbps
```

Obviously we can't send all 20 Gbps through T1.

So the algorithm has to discover something like:

```text
T1 → 10 Gbps
T2 → 10 Gbps
```

which corresponds to:

```text
T1 → 50%
T2 → 50%
```

The actual paper's algorithm works by progressively increasing the **fair share** of Flow Groups until a bottleneck is encountered. 

---

# 7. What is a bottleneck?

This is extremely important.

A **bottleneck** is a link that doesn't have enough remaining capacity to accommodate additional traffic.

Example:

```text
A ─── 100G ─── B
```

If we're already using:

```text
95 Gbps
```

and another Flow Group wants:

```text
20 Gbps
```

we can't put all 20 Gbps there.

That link becomes a bottleneck.

---

# 8. The algorithm's basic behavior

Think of the algorithm like filling glasses with water.

You have:

```text
Glass A
Glass B
Glass C
```

You want to fill them fairly.

You keep increasing everyone together:

```text
A → 1
B → 1
C → 1
```

then:

```text
A → 2
B → 2
C → 2
```

then:

```text
A → 3
B → 3
C → 3
```

But eventually:

```text
Glass B = FULL
```

So you stop increasing B.

Then you continue with the others.

That's the intuition behind the paper's **fair-share** approach.

---

# 9. Now let's use the actual B4 example

The paper gives a concrete example with four sites:

```text
        B
       / \
      /   \
     A     C
      \   /
       \ /
        D
```

There are two Flow Groups:

```text
FG1: A → B
FG2: A → C
```

The example assigns:

```text
FG1 demand = 20 Gbps
FG2 demand = 10 Gbps
```

and considers the available tunnels between the sites. 

---

# 10. Step 1 — Give the Flow Groups their preferred tunnels

The algorithm first considers preferred tunnels.

Conceptually:

```text
FG1:
A → B
A → C → B
A → D → C → B
```

and:

```text
FG2:
A → C
A → B → C
...
```

The algorithm considers the cost and bottlenecks of these tunnels.

The paper describes tunnel cost based on the costs of the edges composing the tunnel. 

---

# 11. Step 2 — Increase fair share

Now imagine B4 starts increasing the fair share.

Something like:

```text
Fair share increases
        ↓
Allocate more bandwidth
        ↓
Check network capacity
        ↓
Bottleneck?
```

If no bottleneck:

```text
Continue
```

If a bottleneck appears:

```text
Freeze affected tunnel
```

That's the key behavior.

---

# 12. What does "freeze" mean?

Suppose:

```text
FG1 → Tunnel T1
```

is using a link that becomes completely full.

B4 essentially says:

> "I can't put any more traffic through this tunnel."

So:

```text
T1
│
├── capacity available? NO
│
└── FREEZE
```

Then the algorithm looks for another suitable tunnel.

This process continues until:

* the Flow Group's demand is satisfied, or
* there are no more useful preferred tunnels.

This is the core intuition of the algorithm. 

---

# 13. Actual result from the paper

For the paper's example, the final allocations include:

### FG2

```text
Tunnel 1 → 30%
Tunnel 2 → 70%
```

So:

```text
       FG2
        │
     ┌──┴──┐
     ▼     ▼
    T1     T2
   30%    70%
```

### FG1

```text
Tunnel 1 → 50%
Tunnel 2 → 40%
Tunnel 3 → 10%
```

So:

```text
             FG1
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
      T1     T2     T3
     50%    40%    10%
```

These are the actual kinds of traffic splits B4 generates before hardware quantization. 

---

# 14. But there's a problem...

Imagine the algorithm says:

```text
Tunnel 1 = 33.333%
Tunnel 2 = 66.667%
```

Can the switch hardware necessarily implement an arbitrary decimal split?

Not necessarily.

So B4 needs another step.

# Quantization

---

# 15. What is quantization?

Think:

```text
Ideal mathematical answer
          ↓
      33.333%
      66.667%
          ↓
      Quantization
          ↓
Hardware-friendly answer
```

The paper describes quantization as changing the split ratios to the granularity supported by the underlying switch hardware. 

So the algorithm may convert:

```text
33.333 / 66.667
```

into something like:

```text
33.5 / 66.5
```

depending on the supported quantum.

---

# 16. Why does B4 need this?

Because software can mathematically say:

```text
Send exactly 33.333333333%
```

but hardware might only support certain discrete ratios.

So:

```text
Software:
"Give me this exact mathematical ratio."

Hardware:
"I support these discrete values."

B4:
"Okay, I'll convert the solution."
```

This is an important **systems engineering** aspect of the paper.

---

# 17. LP vs B4's algorithm

The paper also discusses another important point.

One could formulate the TE problem as a **Linear Program (LP)**.

LP can potentially find an optimal solution.

But there's a problem:

> **The exact LP solution does not scale well.**

B4 therefore designed an algorithm that provides similar fairness and at least **99% bandwidth utilization**, while being about **25× faster than the LP approach** for their deployment. 

This is a **very good seminar point**.

It demonstrates that B4 isn't simply asking:

> "What's the mathematically perfect solution?"

It's asking:

> **"What's a solution that is good enough, fast enough, and scalable enough to run in a real production WAN?"**

That is classic systems research thinking.

# 19. One subtle but important point

You may wonder:

> "Why not just choose the shortest path?"

Because shortest path doesn't necessarily give the best **network-wide utilization**.

Imagine:

```text
                100G
A ───────────────────────── B
 \                         /
  \                       /
   ─────── C ────────────
           100G
```

If everything chooses the shortest path, that path can become heavily congested while another path sits underutilized.

B4 instead asks:

> **How can I distribute traffic across multiple available paths so that the network is used more effectively?**

That's the entire reason traffic engineering exists.

---

# 🎯 Three questions you absolutely need to know

### Q1. Why doesn't B4 simply use the shortest path?

**Answer:**

> Because shortest-path routing can create congestion on some links while leaving other available paths underutilized. B4 uses traffic engineering to distribute traffic across multiple paths and improve overall bandwidth utilization.

### Q2. Why doesn't B4 simply use the exact LP solution?

**Answer:**

> The paper says the LP approach does not scale well. B4 therefore uses a faster algorithm that achieves similar fairness and at least 99% bandwidth utilization, while being about 25× faster than the LP approach in their deployment. 

### Q3. Why is quantization necessary?

**Answer:**

> Because the ideal mathematical traffic split may have finer granularity than the underlying switch hardware supports. B4 therefore converts the ideal split into hardware-supported ratios.

You now understand **why B4 needs the TE algorithm** and roughly **how it works**.
