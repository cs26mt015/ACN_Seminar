## 1. First, don't look at all the boxes

At first glance, it looks complicated:

```text
             GLOBAL LAYER
       ┌──────────────────────┐
       │ Central TE Server     │
       │ SDN Gateway           │
       └──────────┬───────────┘
                  │
        ──────────┼──────────
                  │
        SITE CONTROLLER LAYER
        ┌─────────┴─────────┐
        │                   │
   Site A Controllers   Site B Controllers
        │                   │
        ▼                   ▼
        NCS                 NCS
        OFC                 OFC
        │                   │
        └─────────┬─────────┘
                  │
             SWITCH HARDWARE
        ┌─────────────────────┐
        │   B4 WAN switches   │
        │   OFA / OpenFlow    │
        └─────────────────────┘
```

Don't memorize every box.

The key idea is simply:

> **B4 separates global network decisions, site-level control, and packet forwarding.**

The paper explicitly describes these as three layers: **global**, **site controllers**, and **switch hardware**. 

---

# 2. Layer 1 — Global layer

At the top you have things such as:

* **Central TE Server**
* **SDN Gateway**

The **Central TE Server** is the brain that makes the big traffic-engineering decisions.

For example, imagine:

```text
Site A ───────────── Site B
   \                    /
    \                  /
     ───── Site C ─────
```

Suppose Site A wants to send a huge amount of data to Site B.

The TE server asks:

> "How should I distribute this traffic across the available paths?"

Maybe:

```text
Path 1: A → B       40%
Path 2: A → C → B   60%
```

That is a **global decision**.

The central TE system therefore needs a view of the network that is broader than one individual switch.

---

# 3. Why is it called "logically centralized"?

This is an important seminar/Q&A question.

You might look at:

```text
              Central TE Server
                     │
                     ▼
                  B4 WAN
```

and think:

> "If that server crashes, doesn't the entire B4 network stop?"

Not necessarily.

The paper says the global-layer applications are **replicated across multiple WAN sites**, with leader election selecting the primary instance. 

So mentally think:

```text
          TE Server replicas

          ┌───────────┐
          │ TE Server │ ← PRIMARY
          └───────────┘
                │
      ┌─────────┴─────────┐
      │                   │
┌───────────┐       ┌───────────┐
│ Standby   │       │ Standby   │
│ Server    │       │ Server    │
└───────────┘       └───────────┘
```

There is **one logical decision-making service**, but multiple physical instances provide fault tolerance.

### Professor might ask:

**Q: What does logically centralized mean?**

Good answer:

> "It means B4 has a centralized view and centralized decision-making model, but the actual service is replicated across multiple physical servers for fault tolerance."

That's a very good seminar answer.

---

# 4. Layer 2 — Site Controllers

Now move one level down.

Each site has controllers.

For example:

```text
             Central TE
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Site A      Site B     Site C
   Controller  Controller  Controller
```

The paper calls these **Network Control Servers (NCS)**.

Inside this layer are things such as:

* OpenFlow Controller (**OFC**)
* Network Control Applications (**NCA**)

The important distinction is:

### TE Server

Thinks about:

> **"What should the entire WAN do?"**

### Site controller

Thinks about:

> **"How do I make my site's switches do that?"**

That distinction is extremely important.

---

# 5. Layer 3 — Switch hardware

At the bottom are the actual switches.

These are responsible for the thing that ultimately matters:

> **moving packets.**

So:

```text
TE Server
   │
   │ "Send 60% through this path"
   ▼
Site Controller
   │
   │ "Program these switch rules"
   ▼
Switch
   │
   ▼
PACKETS
```

The switch isn't deciding the entire WAN strategy.

It receives forwarding instructions and actually forwards packets.

The paper describes the switch side as containing an **OpenFlow Agent (OFA)** that receives OpenFlow commands and translates them into commands understood by the switch hardware. 

---

# 6. The most important mental model

Remember this:

```text
             B4
              │
     ┌────────┴─────────┐
     │                  │
  DECISION            ACTION
     │                  │
     ▼                  ▼
 TE Server          Switches
     │                  │
 "What should       "Actually
  happen?"           forward"
     │                  │
     └───────┬──────────┘
             │
        Site Controllers
```

Or even simpler:

> **TE Server = brain**
> **Controller = translator/coordinator**
> **Switch = muscle**

That's a very useful way to explain B4 verbally.

---

# 7. What is the SDN Gateway doing?

This is another box students often get confused about.

The **SDN Gateway** hides the low-level OpenFlow and switch-hardware details from the global applications.

So imagine:

```text
          Central TE Server
                 │
                 │
                 ▼
           SDN Gateway
                 │
        "Don't worry about
         switch details"
                 │
                 ▼
        Site Controllers
                 │
                 ▼
             Switches
```

The TE server shouldn't need to know:

> "Which exact hardware table entry do I modify?"

Instead it can express a higher-level networking decision.

The lower layers deal with the implementation details.

The paper specifically describes the SDN Gateway as abstracting OpenFlow and switch hardware details from the central TE server. 

---

# 8. One very important B4 design decision

Here's something that makes B4 particularly interesting.

B4 **didn't throw away traditional routing**.

It kept existing routing mechanisms such as:

* BGP
* IS-IS

and layered traffic engineering on top of them. 

So don't think:

```text
Old routing ❌
       ↓
SDN completely replaces it
```

Instead:

```text
        B4

   Traffic Engineering
          ↑
      OpenFlow
          ↑
   Existing Routing
   (BGP / IS-IS)
```

This is a **layering approach**.

And there's a clever safety feature:

> If traffic engineering has a problem, B4 can disable TE and fall back to shortest-path forwarding.

The paper calls this essentially a **"big red button"** design. 

That's a fantastic point to mention during your seminar because it shows that B4 wasn't just designed for performance—it was designed with operational safety in mind.

---

# 9. Why did B4 use this architecture?

This connects directly to the paper's design philosophy.

Google wanted:

```text
Existing routing
       +
Centralized traffic engineering
       +
Programmable switches
       +
Operational safety
```

rather than completely replacing everything.

The design decisions table in the paper highlights this philosophy, including centralized traffic engineering, separate software/hardware concerns, and the ability to fall back to traditional forwarding. 

---

# 10. A real example

Let's say:

```text
Google Site A
      │
      │ 100 Gbps traffic
      ▼
Google Site B
```

There are two possible paths:

```text
Path 1:
A ─────────────── B

Path 2:
A ───── C ─────── B
```

The TE server determines:

```text
Path 1 → 40%
Path 2 → 60%
```

Then:

### Step 1 — Global decision

```text
TE Server

40% → Path 1
60% → Path 2
```

### Step 2 — Controller

The site controller converts that decision into switch programming.

### Step 3 — OpenFlow

The controller programs the relevant switch tables.

### Step 4 — Packet arrives

The source switch identifies the traffic and hashes flows into the selected tunnels according to the desired ratio.

### Step 5 — Packets travel

```text
             40%
A ───────────────── B
 \
  \ 60%
   C ───────────── B
```

That is B4 in action.

# 11. What you should be able to say in your seminar

If your architecture slide is displayed, you should be able to say something like:

> "B4 uses a three-layer software-defined architecture. At the top, logically centralized applications such as the Central TE Server make global traffic-engineering decisions. The site-controller layer contains Network Control Servers and OpenFlow Controllers that translate these decisions into switch-level operations. Finally, the switch hardware forwards packets, with an OpenFlow Agent translating OpenFlow commands into hardware-specific operations. B4 also retains existing BGP and IS-IS routing and layers centralized traffic engineering on top of it."

That is already a **strong seminar explanation**.

# 12. Professor Q&A you should prepare

### Q1. Why not put all intelligence directly into the switches?

**Answer:**

Because B4 wanted the global traffic-engineering logic to have a network-wide view while keeping switch hardware relatively simple and programmable.

---

### Q2. Is B4 completely replacing BGP/IS-IS?

**Answer:**

No. B4 retains BGP and IS-IS for baseline routing and layers traffic engineering on top of them. 

---

### Q3. What happens if the TE system fails?

**Answer:**

B4 is designed to fall back to shortest-path forwarding by disabling traffic engineering, providing an operational recovery mechanism. 

---

### Q4. Why is the TE server "logically centralized" instead of simply centralized?

**Answer:**

Because the service is replicated across multiple physical servers for fault tolerance, while presenting a centralized logical decision-making model. 

---

### Q5. What is the role of OpenFlow?

**Answer:**

OpenFlow provides the mechanism through which the controller programs the switches, while the OpenFlow Agent translates those commands into switch-specific operations.
