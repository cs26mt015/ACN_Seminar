Perfect. Now we can study the **actual B4 architecture** from the paper.

The key thing I want you to understand is that B4 is **not simply “one big central controller controlling every switch.”** It has a carefully designed hierarchy.

---

# 1. The B4 architecture at a high level

The paper divides B4 logically into **three layers**: 

```text
┌─────────────────────────────────────────────┐
│              GLOBAL LAYER                   │
│                                             │
│     Central TE Server + SDN Gateway         │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│            SITE CONTROLLER LAYER            │
│                                             │
│ Network Control Servers (NCS)               │
│   ├── OpenFlow Controllers (OFC)            │
│   └── Network Control Applications (NCA)    │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│              SWITCH HARDWARE                │
│                                             │
│     OpenFlow Agent → forwarding hardware    │
└─────────────────────────────────────────────┘
```

Let's understand each layer.

---

# 2. Layer 1 — Switch Hardware

At the bottom we have the actual switches.

```text
        ┌───────────────┐
        │    SWITCH     │
        │               │
Packets │  Forwarding   │
───────►│    Hardware   │──────►
        │               │
        └───────────────┘
```

The important B4 design decision was:

> **Keep the switch hardware relatively simple and primarily use it for forwarding.**

The paper explicitly says the switch hardware layer primarily forwards traffic and does not run complex control software. 

This is one of the major ideas behind B4.

---

# 3. Why make the switches simpler?

Traditional WAN routers can contain lots of functionality:

```text
Router
 ├── Routing protocols
 ├── Large forwarding tables
 ├── Deep buffers
 ├── High availability mechanisms
 └── Other control functionality
```

B4 moved much of that software functionality away from the switch.

Why?

The paper gives several reasons.

### Reason 1 — B4 had relatively few sites

Because B4 connected a relatively small set of data centers, it didn't need enormous forwarding tables.

### Reason 2 — Google's applications could manage transmission rates

This reduced the need for extremely deep buffers.

### Reason 3 — Software failures were an important concern

Moving software functionality away from the hardware allowed Google to use distributed-systems techniques for software fault tolerance.

These design decisions are summarized in the paper's design table and switch-design section.  

---

# 4. Layer 2 — Site Controller

Now we move upward.

Every B4 site has **Network Control Servers**, or **NCS**.

Think:

```text
                B4 SITE

      ┌────────────────────────┐
      │ Network Control        │
      │ Servers (NCS)          │
      │                        │
      │  ┌──────┐   ┌──────┐  │
      │  │ OFC  │   │ NCA  │  │
      │  └──────┘   └──────┘  │
      └───────────┬────────────┘
                  │
          ┌───────┼───────┐
          ▼       ▼       ▼
       Switch   Switch   Switch
```

The NCS hosts two important types of software:

### OFC

**OpenFlow Controller**

It communicates with the switches.

### NCA

**Network Control Application**

These applications provide network-control functionality.

The paper explicitly says the site-controller layer consists of NCS hosting both OFCs and NCAs. 

---

# 5. What does the OpenFlow Controller do?

Let's simplify it.

```text
        OFC
         │
         │ OpenFlow
         ▼
      Switch
```

The OFC maintains network state and tells switches what forwarding entries should be installed.

The paper says OFCs maintain network state based on NCA directives and switch events, then instruct switches to set forwarding-table entries based on that changing state. 

So:

```text
Network event
     ↓
OFC learns about it
     ↓
Network state changes
     ↓
OFC determines forwarding state
     ↓
OpenFlow commands
     ↓
Switch
```

---

# 6. What is an NCA?

NCA = **Network Control Application**.

Don't overcomplicate this.

Think of an NCA as software that says:

> "Given what I know about the network, what should the network be doing?"

The OFC is more concerned with communicating that control state to switches.

So:

```text
NCA
 │
 │ "I want this network state"
 ▼
OFC
 │
 │ OpenFlow
 ▼
Switch
```

Later, the **TE system** will become one of the important sources of these network-control decisions.

---

# 7. Layer 3 — Global Layer

Now we reach the interesting part.

B4 has a **global layer** containing logically centralized applications.

Two examples given by the paper are:

* **SDN Gateway**
* **Central TE Server**



Conceptually:

```text
             GLOBAL LAYER

       ┌─────────────────────┐
       │   Central TE Server │
       └──────────┬──────────┘
                  │
       ┌──────────▼──────────┐
       │     SDN Gateway     │
       └──────────┬──────────┘
                  │
                  ▼
            Site Controllers
```

---

# 8. What does "logically centralized" mean?

This is an important phrase.

It does **not** necessarily mean:

> "There is physically one computer."

Instead:

> The system behaves as one centralized service from the network's point of view.

Why?

Because the global applications were replicated across multiple WAN sites for fault tolerance.

The paper says global-layer applications were replicated across multiple WAN sites, with separate leader election to determine the primary instance. 

So conceptually:

```text
           LOGICAL SERVICE
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Server A  Server B  Server C
       │         │         │
       └─────────┼─────────┘
                 │
          one primary
          at a time
```

This gives you centralized behavior without relying on a single physical machine.

---

# 9. Why is the SDN Gateway needed?

This is a really nice design detail.

The paper says:

> The SDN Gateway abstracts OpenFlow and switch-hardware details from the central TE server. 

Think of it as an **adapter**.

Without the gateway:

```text
Central TE
    │
    │ must understand
    │ OpenFlow + hardware
    ▼
Switches
```

With the gateway:

```text
Central TE
    │
    │ high-level network intent
    ▼
SDN Gateway
    │
    │ handles OpenFlow details
    ▼
Site Controllers
    │
    ▼
Switches
```

This separation makes the central TE system less dependent on the exact details of switch hardware.

---

# 10. Now put all three layers together

Here's the diagram I want you to remember:

```text
                     GLOBAL LAYER
        ┌────────────────────────────────┐
        │                                │
        │       Central TE Server        │
        │              │                 │
        │              ▼                 │
        │         SDN Gateway            │
        └──────────────┬─────────────────┘
                       │
                       ▼
                 SITE CONTROLLER
        ┌────────────────────────────────┐
        │        Network Control         │
        │           Servers              │
        │                                │
        │     ┌───────┐    ┌───────┐     │
        │     │  OFC  │    │  NCA  │     │
        │     └───┬───┘    └───────┘     │
        └─────────┼──────────────────────┘
                  │
              OpenFlow
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
       SWITCH  SWITCH    SWITCH
          │       │        │
          └───────┴────────┘
              DATA PLANE
```

This is essentially the architecture you should understand before studying B4's TE mechanism. 

---

# 11. Now there's another clever part: routing

Here's something important.

B4 didn't say:

> "Forget everything that existed before. We'll create a completely new routing system."

Instead, it retained existing routing protocols.

The paper says B4 supported existing distributed routing protocols for interoperability and gradual deployment. 

So:

```text
              B4
               │
       ┌───────┴────────┐
       │                │
   Traditional       New SDN
    Routing           System
       │                │
    BGP/IS-IS       OpenFlow/TE
```

This was an important deployment decision.

---

# 12. The "big red button"

This is one of my favorite B4 concepts because it makes the architecture easy to remember.

B4 layered TE **on top of** baseline routing.

So:

```text
              Forwarding
                  ▲
                  │
        ┌─────────┴─────────┐
        │                   │
     TE rules          Shortest path
        │                   │
        └─────────┬─────────┘
                  │
             Base routing
```

If TE is working:

```text
Traffic
   ↓
TE
   ↓
Multipath forwarding
```

If TE has a critical problem:

```text
Disable TE
   ↓
Fall back
   ↓
Shortest-path forwarding
```

The paper explicitly describes this isolation as a **“big red button”** because operators could disable TE and fall back to shortest-path forwarding. It says this fault-recovery mechanism proved valuable. 

This is an excellent example of a **design decision motivated by reliability**.

---

# 13. One more important concept: B4 site abstraction

This part can initially look confusing.

Imagine a B4 site contains many switches:

```text
                  SITE A

       ┌───────┐  ┌───────┐
       │Switch1│  │Switch2│
       └───┬───┘  └───┬───┘
           │          │
       ┌───┴───┐  ┌───┴───┐
       │Switch3│  │Switch4│
       └───────┘  └───────┘
```

There might be **hundreds of ports** connecting that site to remote sites.

The global TE system doesn't want to treat every individual physical link as a separate global node.

Instead, B4 abstracts the whole site as:

```text
               SITE A
                  │
             100 Gbps
                  │
                  ▼
               SITE B
```

So:

```text
Physical reality:

Switch ──┐
Switch ──┼──── Site B
Switch ──┤
Switch ──┘


TE's abstraction:

Site A ───────── Site B
```

The paper says TE abstracts each site into a single node with a single edge of given capacity to each remote site. 

---

# 14. But there's a problem

Suppose Site A has four physical links to Site B:

```text
Site A                 Site B

Switch 1 ────────────────┐
Switch 2 ────────────────┤
Switch 3 ────────────────┤
Switch 4 ────────────────┘
```

If TE sees them as one logical connection:

```text
Site A ═══════════════ Site B
```

traffic needs to be distributed across those physical links.

B4 therefore uses a **custom variant of ECMP hashing** to balance traffic across the links. 

So:

```text
              Logical edge
Site A ═══════════════════ Site B
          │    │    │
          ▼    ▼    ▼
        Link1 Link2 Link3
```

This allows the global TE system to work with a simpler topology while the underlying switches handle distribution across the physical links.

---

# 15. And finally: the OpenFlow Agent

There's one more box we need.

Inside the switch:

```text
┌─────────────────────────────┐
│           SWITCH            │
│                             │
│   ┌─────────────────────┐   │
│   │   OpenFlow Agent    │   │
│   └──────────┬──────────┘   │
│              │              │
│              ▼              │
│     Forwarding Hardware     │
└─────────────────────────────┘
```

The **OpenFlow Agent (OFA)** is software running on the switch.

It connects to the remote OpenFlow Controller.

The paper says it accepts OpenFlow commands and forwards relevant packets/events to the controller. It also translates OpenFlow messages into driver commands that configure the switch-chip forwarding tables. 

So the complete path becomes:

```text
Central TE
    ↓
SDN Gateway
    ↓
Site NCA / OFC
    ↓
OpenFlow
    ↓
OpenFlow Agent
    ↓
Switch hardware
    ↓
Packet forwarding
```

---

# 16. The architecture in one sentence

If your professor asks:

> **"Explain B4 architecture in simple terms."**

Your mental answer should be:

> **B4 separates network control from packet forwarding: centralized global applications such as the TE server make network-wide decisions, site-level controllers translate those decisions into switch control, and relatively simple switches execute the forwarding.**

That captures the core architecture described by the paper.
