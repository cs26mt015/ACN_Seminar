# Figure 4 — How a packet actually travels through B4

Now we're going to make everything **concrete**.

You've learned:

* routing
* TE
* Flow Groups
* Tunnel Groups
* OpenFlow
* ACL
* Multipath tables
* encapsulation

But the natural question is:

> **"Okay, when an actual packet enters a B4 switch, what exactly happens to it?"**

Figure 8 in the paper gives a **Multipath WAN Forwarding Example**. This is one of the best figures for understanding the actual packet journey. 

---

# 1. Let's create a simple B4 network

Imagine:

```text
                Transit Switch 2
                     /\
                    /  \
                   /    \
                  /      \
        Transit Switch 1
              /           \
             /             \
            ▼               ▼
      Encapsulation      Decap
         Switch           Switch
            │                │
            ▼                ▼
         Host A            Host B
```

The actual paper's Figure 8 shows an encapsulation switch, two transit switches, and a decapsulation switch. 

The important thing is that **the packet doesn't simply follow ordinary shortest-path forwarding**.

B4 has decided that this traffic should use a particular tunnel.

---

# 2. A packet arrives

Suppose Host A sends:

```text
Source = 10.0.0.1
Destination = 9.0.0.1
```

The packet arrives at the **encapsulation switch**.

Initially:

```text
┌─────────────────────────────┐
│ Source: 10.0.0.1           │
│ Destination: 9.0.0.1       │
│ Payload                     │
└─────────────────────────────┘
```

The destination is still the **real destination**:

```text
9.0.0.1
```

---

# 3. The switch checks its forwarding information

Remember what we learned earlier.

B4 has:

```text
LPM table
ACL table
Multipath table
Encapsulation Tunnel table
```

The incoming packet may match both:

```text
LPM
```

and:

```text
ACL
```

But the ACL has **strict precedence** over the LPM table. 

So conceptually:

```text
Packet
  │
  ▼
ACL
  │
  ├── TE rule matches → continue with TE
  │
  └── no TE rule → normal LPM forwarding
```

---

# 4. The ACL identifies the traffic

Suppose the packet belongs to:

```text
FG = A → B
```

and that Flow Group has:

```text
Tunnel Group:
T1 → 40%
T2 → 60%
```

The ACL tells the switch:

> "This packet should use the multipath TE treatment."

---

# 5. The Multipath Table chooses a tunnel

Now the packet goes through the multipath logic.

Conceptually:

```text
                 Packet
                    │
                    ▼
               Multipath
                 Table
                    │
              ┌─────┴─────┐
              ▼           ▼
           Tunnel 1     Tunnel 2
             40%           60%
```

The switch uses hashing to distribute packets/flows according to the desired tunnel ratio. 

So our particular packet might be assigned:

```text
Tunnel 2
```

---

# 6. Now comes the clever part — encapsulation

The switch doesn't simply send the packet normally.

It adds an **outer IP header**.

Before:

```text
┌───────────────────────────┐
│ Original IP header        │
│                           │
│ src = 10.0.0.1            │
│ dst = 9.0.0.1             │
├───────────────────────────┤
│ Payload                   │
└───────────────────────────┘
```

After encapsulation:

```text
┌───────────────────────────┐
│ OUTER IP HEADER           │
│ tunnel information        │
├───────────────────────────┤
│ ORIGINAL IP HEADER        │
│ src = 10.0.0.1            │
│ dst = 9.0.0.1             │
├───────────────────────────┤
│ Payload                   │
└───────────────────────────┘
```

This is the basic idea of B4's IP-in-IP tunnel implementation. 

---

# 7. Why do we need an outer header?

This is a **very important "why" question**.

Imagine the original packet says:

```text
Destination = 9.0.0.1
```

Normally, routers would use that destination to determine where to send it.

But B4 wants to say:

> "Don't just take the ordinary route. I specifically want this packet to follow my selected tunnel."

So B4 adds tunnel information:

```text
OUTER HEADER
     ↓
"Follow this tunnel"

INNER HEADER
     ↓
"Eventually deliver to 9.0.0.1"
```

That's the key idea.

---

# 8. Think of it like putting a package inside another package

This analogy is useful for your seminar.

Imagine you have:

```text
Package:
"Send to Mickey"
```

But you want a courier to take a special route.

So you put it inside another package:

```text
Outer package:
"Take this package through Route X"

Inside:
"Final recipient = Mickey"
```

B4 does something conceptually similar:

```text
Outer header → tunnel path
Inner header → actual packet destination
```

---

# 9. Now the packet reaches a transit switch

The transit switch doesn't need to understand the original application.

It primarily looks at the **outer/tunnel information**.

So:

```text
               Transit Switch
                     │
             Read tunnel info
                     │
                     ▼
              Which tunnel?
                     │
                     ▼
                Next hop
```

This is one of the advantages of the tunnel abstraction.

The paper describes transit switches as forwarding packets based on the outer header. 

---

# 10. The packet can pass through multiple transit switches

For example:

```text
Host A
  │
  ▼
Encap
  │
  ▼
Transit 1
  │
  ▼
Transit 2
  │
  ▼
Decap
  │
  ▼
Host B
```

The transit switches don't have to redo the entire global TE calculation.

The TE decision was already made.

They simply implement the tunnel forwarding.

---

# 11. Destination switch = decapsulation

Eventually the packet reaches the destination switch.

Now the switch recognizes:

> "This packet has reached the end of its tunnel."

So it removes the outer header.

Before:

```text
┌─────────────────────────────┐
│ Outer tunnel header         │
├─────────────────────────────┤
│ Original header             │
│ Destination = 9.0.0.1      │
├─────────────────────────────┤
│ Payload                     │
└─────────────────────────────┘
```

After:

```text
┌─────────────────────────────┐
│ Original header             │
│ Destination = 9.0.0.1      │
├─────────────────────────────┤
│ Payload                     │
└─────────────────────────────┘
```

Then the destination switch forwards the packet normally using the inner packet information.

The paper explicitly describes this sequence: source encapsulates, transit switches forward based on the outer header, and the destination decapsulates before normal forwarding. 

---

# 12. Full packet journey

This is the diagram I want you to understand:

```text
                    B4 WAN

Host A
  │
  │ Original packet
  │ dst = 9.0.0.1
  ▼
┌───────────────┐
│ ENCAP SWITCH  │
└───────┬───────┘
        │
        │ 1. Identify Flow Group
        │
        ▼
    ACL / TE rule
        │
        │ 2. Select multipath
        ▼
   Tunnel 1 / Tunnel 2
        │
        │ 3. Add outer header
        ▼
┌───────────────┐
│   TRANSIT 1   │
└───────┬───────┘
        │
        │ 4. Forward using
        │    tunnel information
        ▼
┌───────────────┐
│   TRANSIT 2   │
└───────┬───────┘
        │
        ▼
┌───────────────┐
│ DECAP SWITCH  │
└───────┬───────┘

        ▼

        │
        │ 6. Normal forwarding
        ▼
```

If you can explain this diagram without looking at notes, you understand B4's forwarding mechanism.

# 13. Now connect it to the previous lesson

Remember we had:

```text
FG1:
T1 → 50%
T2 → 40%
T3 → 10%
```

The TE algorithm produced that.

Then OpenFlow implements it.

So:

```text
TE Algorithm
     │
     │
     ▼
"FG1 = 50/40/10"
     │
     ▼
OpenFlow programming
     │
     ▼
Multipath table
     │
     ▼
Hashing
     │
     ▼
Actual packets
```

This is the complete chain from **algorithm → hardware → packet**.

# 14. One subtle detail: multiple sites must be configured

There's another important point from the paper.

A tunnel isn't just a rule at the source.

Suppose:

```text
A → C → B
```

To create that tunnel, the relevant switches at multiple sites need appropriate configuration.

The paper notes that installing a tunnel therefore requires configuring multiple sites. 

So conceptually:

```text
       Tunnel A → C → B

A switch        C switch        B switch
   │               │               │
   │ configured    │ configured    │ configured
   └───────────────┴───────────────┘
```

This becomes important later when we study **TE state coordination and failures**.

---

# 15. How does B4 know what the destination normally is?

Remember:

```text
BGP / IS-IS
     ↓
Routing information
     ↓
LPM table
```

The paper says B4 continues to use the existing shortest-path routing information, including LPM entries from BGP, even while TE is operating. 

So TE doesn't destroy the normal forwarding mechanism.

It sits **on top of it**.

---

# 16. Very important distinction

Don't say:

> "The tunnel replaces routing."

That's not quite right.

Instead say:

> **"The tunnel provides a TE-controlled forwarding path, while the underlying routing system remains available for normal forwarding and as a fallback."**

That's much more accurate.

---

# 17. Professor Q&A

### Q1. Why does B4 use encapsulation?

**Answer:**

> To carry traffic along the selected TE tunnel. The outer header identifies the tunnel path, while the inner packet retains the original destination information. 

---

### Q2. What does a transit switch look at?

**Answer:**

> It forwards based on the outer tunnel information rather than making the original global TE decision again. 

---

### Q3. What happens at the destination?

**Answer:**

> The destination switch decapsulates the packet, removing the tunnel header, and then forwards the original packet using normal routing information. 

---

### Q4. Why does B4 need both ACL and LPM?

**Answer:**

> LPM provides normal shortest-path forwarding, while the ACL identifies traffic that should receive TE treatment. The ACL has precedence over LPM. 

---

### Q5. Does every packet get encapsulated?

**Answer:**

Not necessarily.

The important distinction is:

```text
TE rule matches?
       │
   ┌───┴───┐
  YES      NO
   │        │
   ▼        ▼
 TE path   Normal
/tunnel   routing
```

B4 supports the coexistence of shortest-path routing and TE.
