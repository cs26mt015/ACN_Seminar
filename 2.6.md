# B4 Results — Did it actually work?

Now we are at the part that can make your seminar **much stronger than a simple "this is what B4 does" presentation**.

A research paper is not just:

> "Here is our system."

It also needs to answer:

> **"Does the system actually work?"**

B4 has unusually strong evidence because the paper reports **real production deployment**, not just a simulation. The authors describe deployment statistics, algorithm performance, failure experiments, throughput improvement, link utilization, and a real outage. 

---

# 1. First result: B4 was actually deployed

This is the first thing you should remember.

B4 was not merely a theoretical architecture.

The paper reports production deployment across:

```text
16 sites
46 unidirectional edges
240 Tunnel Groups
2700 Flow Groups
350 tunnels in use
1150 cached tunnels
```

during the September–November 2012 period. 

It also reports roughly:

```text
286 topology changes/day
7 edge additions/deletions/day
```

So B4 was dealing with a **real, changing WAN**.

---

# 2. Why is this important for your seminar?

Because you can say:

> "B4 was not just proposed and evaluated in a laboratory environment. The system was deployed in Google's production WAN and operated at significant scale."

That immediately makes the paper more interesting.

---

# 3. TE algorithm performance

Remember our previous lesson:

```text
TE Algorithm
     ↓
Calculate traffic allocation
     ↓
Program network
```

A natural question is:

> **"How long does the algorithm take?"**

The paper reports:

```text
Average runtime = 0.3 seconds
Maximum runtime = 0.8 seconds
```

and approximately:

```text
540 algorithm runs/day
```

in the reported deployment period. 

That's an important result.

It tells us that the algorithm is not some enormous computation that takes minutes or hours.

---

# 4. Why does runtime matter?

Imagine traffic demand changes.

```text
10:00
Demand A = 20 Gbps

10:01
Demand A = 40 Gbps

10:02
Demand A = 10 Gbps
```

If the TE algorithm took:

```text
20 minutes
```

to calculate a new allocation, it wouldn't be very useful for dynamic traffic engineering.

But if it takes fractions of a second:

```text
~0.3 seconds average
```

the system can react much more quickly.

That's one reason the paper emphasizes a scalable algorithm rather than simply using an exact but expensive optimization formulation. 

---

# 5. But algorithm speed isn't the whole story

Here's a very important systems lesson.

Suppose:

```text
TE calculation = 0.3 sec
```

Great.

But what if programming the switches takes:

```text
5 seconds
```

?

Then the overall system isn't really 0.3 seconds.

And this is exactly what the B4 paper discovered.

The paper's TE operation measurements show that a substantial fraction of the latency came from **switch programming**, rather than the optimization computation itself. 

---

# 6. This is a great research insight

You can think of the process as:

```text
TE Server
   │
   │ Calculate solution
   │ ~0.3 sec
   ▼
TE operations
   │
   │
   ▼
OpenFlow / switch programming
   │
   │ potentially slower
   ▼
Hardware tables updated
```

So:

> **Computing the decision was relatively fast; applying the decision to the hardware was a significant operational cost.**

That's a much more interesting observation than simply saying:

> "The algorithm runs in 0.3 seconds."

---

# 7. Failure testing

Now let's ask:

> **"What happens if something breaks?"**

The authors explicitly tested several failure types.

The paper reports:

| Failure                                         | Packet loss |
| ----------------------------------------------- | ----------: |
| Single link                                     |    **4 ms** |
| Encapsulation switch                            |   **10 ms** |
| Transit switch neighboring encapsulation switch | **3300 ms** |
| OFC                                             |    **0 ms** |
| TE server                                       |    **0 ms** |
| TE disable/enable                               |    **0 ms** |



Don't try to memorize all six numbers yet.

The important pattern is:

```text
Most failures → very small / zero observed loss

One important case:
Transit switch near encapsulation switch
→ ~3.3 seconds
```

---

# 8. Why did the transit-switch failure take longer?

This is a nice professor question.

Suppose:

```text
Encap
  │
  ▼
Transit X  ← FAILS
  │
  ▼
Destination
```

The neighboring encapsulation switch may have multiple tunnel entries that were traversing the failed switch.

The network therefore needs to reconverge and update forwarding behavior.

The paper says this case took about **3.3 seconds**, largely because the neighboring encapsulation switch had to update multiple tunnel entries associated with the failed switch. 

---

# 9. What about the TE server failing?

Interestingly:

```text
TE Server failure
       ↓
0 ms packet loss
```

Why?

Because the forwarding state already installed in the network can continue operating.

Think:

```text
TE Server
    X
    │
    │
    ▼
Existing switch state
    │
    ▼
Packets continue
```

The control system being temporarily unavailable doesn't automatically mean the data plane immediately stops forwarding.

That's an important SDN concept.

---

# 10. What about disabling TE?

The paper reports:

```text
TE Disable / Enable
        ↓
0 ms packet loss
```

Why?

Because B4 was designed so that TE could be disabled and the network could fall back to its underlying routing behavior.

This connects directly to the **"big red button"** idea we discussed earlier. 

---

# 11. Now the BIG result — throughput

This is probably one of the **best numbers for your presentation**.

The paper compares B4's TE allocation against shortest-path routing.

The result:

> **14% average throughput improvement.**

The paper says this improvement is substantial, particularly during periods of high demand. 

So:

```text
Shortest-path routing
        │
        │ baseline
        ▼
       100%
        │
        │ B4 TE
        ▼
      +14% average
```

Don't interpret this as:

> "Every application becomes 14% faster."

That's not what the paper says.

It's an **average throughput improvement relative to shortest-path routing** in the evaluation.

---

# 12. Why does B4 improve throughput?

This should now be easy for you.

Shortest path:

```text id="v9y68c"
       ┌────── shortest ──────┐
A ─────┤                       ├── B
       └──── alternative ──────┘
```

may concentrate traffic on one path.

B4 says:

```text id="m6y5yb"
Don't use only the shortest path.

Use:
Path 1 → some traffic
Path 2 → some traffic
Path 3 → some traffic
```

So more of the available network capacity can be used.

---

# 13. More paths help — but only up to a point

This is a particularly nice result from Figure 13.

The paper evaluates throughput as the maximum number of paths available increases.

The curve roughly behaves like:

```text id="h2e6ij"
Throughput
   │
   │                  ______
   │             ____/
   │         ___/
   │     ___/
   │____/
   └────────────────────────
      1  2  3  4  5  6...
          # paths
```

The improvement **flattens around 4 paths**. 

So B4 doesn't need to use an enormous number of paths.

The paper's deployment therefore used:

> **4 paths**

as the maximum.

That's a nice engineering trade-off:

```text
More paths
    ↓
Potentially better utilization
    ↓
But also more complexity
    ↓
Improvement eventually flattens
    ↓
Choose 4
```

---

# 14. Path split granularity also matters

Remember **quantization**?

The paper also evaluates how finely traffic can be divided.

Conceptually:

```text
Coarse split
   ↓
Less flexibility

Fine split
   ↓
More flexibility
```

The improvement flattens around a **1/16 path-split quantum**. The deployment used a **1/4 quantum** with four paths. 

This is another excellent example of engineering trade-offs.

---

# 15. Here's a surprisingly useful example

The paper gives an example involving a **high-priority weekly data copy**.

Suppose:

```text
Weekly high-priority copy
        │
        ▼
Shortest path
```

Moving it to an alternative route only improved weekly average utilization by around:

```text
5%
```

That doesn't sound huge.

But the paper notes that this could **halve the required deployed capacity**. 

That's a powerful point.

It shows that:

> **Average utilization isn't always the same thing as infrastructure cost.**

A small utilization improvement at the right time can have a very large effect on how much capacity needs to be deployed.

---

# 16. Link utilization — another major result

Traditional WANs often deliberately operate below full utilization.

The paper contrasts this with B4.

B4's edges were able to run at **near 100% utilization**, while using traffic priorities to protect important traffic. 

Think:

```text
Traditional WAN:

Capacity
100% ─────────────────
       █████████
       █████
       ███
       ↑
     ~30–40%
```

versus B4:

```text
B4:

100% ─────────────────
██████████████████████
██████████████████████
██████████████████████
```

The exact behavior varies over time, but the key idea is:

> **B4 deliberately drives utilization much higher.**

---

# 17. "But isn't 100% utilization dangerous?"

Excellent question.

Normally, yes.

That's why B4's traffic characteristics matter.

Remember our earlier lesson:

B4's traffic is largely **elastic**.

Some lower-priority applications can:

```text
receive less bandwidth
        ↓
slow down / throttle
```

while high-priority traffic receives stronger protection.

The paper explains that centralized TE can mix traffic classes so that heavily utilized links carry substantial lower-priority traffic, while local QoS mechanisms protect higher-priority traffic from packet loss. 

---

# 18. Hashing also worked well

Remember when we talked about:

```text
Tunnel 1
Tunnel 2
Tunnel 3
```

and hashing distributing traffic?

The paper evaluates per-link utilization inside a trunk and reports encouraging load balancing.

For at least **75% of site-to-site edges**, the max:min utilization ratio across constituent links was:

```text
1.05 without failures
2.0 with failures
```



You don't necessarily need this number on your first presentation slide.

But it's excellent for Q&A.

# 19. Now the most interesting part: the real outage

This is one of the **best storytelling sections for your seminar**.

Why?

Because B4 wasn't perfect.

The authors describe a real outage caused during a planned maintenance operation. 

And this gives you something very valuable:

> **B4's strengths AND its limitations.**

---

# 20. What happened?

During maintenance, operators introduced a new switch.

The new switch accidentally had:

> **the same switch ID as an existing switch.**

That caused substantial link flaps.

Then:

```text
Duplicate switch ID
        ↓
ISIS LSP problems
        ↓
Network topology processing
        ↓
Heavy control-plane load
```

The paper describes this as triggering significant control-plane problems. 

---

# 21. Then the control path became overloaded

The paper describes protocol packets flowing through:

```text
Quagga
  ↓
OFC
  ↓
OFA
```

and a substantial queue building up.

At peak, the protocol packet queue grew beyond:

> **400 MB**



This is a very interesting lesson:

> **The data plane can be fine while the control plane is struggling.**

---

# 22. Then another failure happened

Because the system was overloaded:

```text
ISIS Hellos delayed
       ↓
interfaces considered down
       ↓
BGP adjacencies break
       ↓
routing/control problems
```

So the initial mistake triggered a chain reaction.

---

# 23. What did B4 do during this?

Interestingly, existing TE transit traffic could continue using the **last known state**.

But new tunnel creation was affected because the controllers could no longer reliably communicate.

So:

```text
Existing traffic
      ↓
Last known TE state
      ↓
Can continue

New TE operations
      ↓
Need controller communication
      ↓
Problem
```

This distinction is important.

---

# 24. How did operators recover?

Eventually operators:

```text
1. Drained the site
2. Disabled TE
3. Restarted OFCs
4. Re-established the system
5. Restarted TE
```

The outage became a major source of engineering lessons for the B4 team. 

---

# 25. What did they learn?

This is **gold for your seminar conclusion**.

The paper lists several lessons, including:

### 1. Control-path scalability matters

The communication path between:

```text
OFC ↔ OFA
```

needs to be fast and scalable.

### 2. OFA should be asynchronous and multithreaded

Why?

Because multiple switch chips may need programming in parallel.

### 3. Better performance profiling is needed

The team discovered "warning signs" in logs that should have received more attention.

### 4. Control failures are different from hardware failures

Traditional routing systems may validate forwarding state differently.

B4 needed to distinguish:

```text
Hardware failure
      vs
Control-plane failure
```

and react appropriately.

These lessons are explicitly discussed by the authors after the outage.
