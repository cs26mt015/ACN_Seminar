Excellent. Now we reach the **core of B4's Traffic Engineering**.

# Slide 8 — Flow Groups, Tunnels & Tunnel Groups

This slide is important because the professor can ask:

> **“How exactly does B4 decide which traffic uses which path?”**

The answer starts with three concepts:

**Flow Group → Tunnel → Tunnel Group**

The paper defines these explicitly in its centralized TE architecture. 

---

## 1. First: Why can't B4 handle every application separately?

Imagine Google has thousands of applications sending traffic.

If the TE system tried to calculate a separate decision for every individual application or flow, the problem would become huge.

So B4 **aggregates traffic**.

That's where the **Flow Group (FG)** comes in.

---

# 2. Flow Group — FG

The paper defines a Flow Group as:

> **{source site, destination site, QoS}**

In simple terms:

```text
Flow Group
    =
Where traffic comes from
+
Where traffic is going
+
Its QoS class
```

For example:

```text
FG1 = {Data Center A, Data Center D, High Priority}
```

Another:

```text
FG2 = {Data Center A, Data Center D, Low Priority}
```

Notice something important:

Both are going from **A → D**, but they have different QoS.

Therefore B4 can treat them differently.

The paper uses Flow Groups specifically so TE doesn't have to operate at individual-application granularity. 

---

# 3. Tunnel — T

Now we need to answer:

> **What path should that traffic take?**

That's the job of a **Tunnel**.

A tunnel represents a **site-level path**.

For example:

```text
A → B → D
```

is one tunnel.

Another tunnel could be:

```text
A → C → D
```

And another:

```text
A → E → F → D
```

So:

```text
        Tunnel 1
A ───── B ───── D

        Tunnel 2
A ───── C ───── D
```

The paper says B4 implements these tunnels using **IP-in-IP encapsulation**. 

Don't worry about IP-in-IP yet. We'll cover the actual packet movement in a later slide.

For now remember:

> **Tunnel = one possible site-level path.**

---

# 4. Tunnel Group — TG

Now we have:

```text
Flow Group = what traffic?
Tunnel = which path?
```

But we still need:

> **How much traffic should use each tunnel?**

That's where the **Tunnel Group (TG)** comes in.

A Tunnel Group maps a Flow Group to a set of tunnels and gives each tunnel a **weight**.

For example:

```text
Flow Group:
A → D

Available tunnels:

Tunnel 1: A → B → D
Tunnel 2: A → C → D
```

B4 might decide:

```text
Tunnel 1 → 60%
Tunnel 2 → 40%
```

So the Tunnel Group is effectively saying:

```text
FG: A → D
       │
       ├── Tunnel 1 → 60%
       │
       └── Tunnel 2 → 40%
```

The paper defines the weight as the fraction of the Flow Group's traffic forwarded along that tunnel. 

---

# 5. Put everything together

This is the diagram I want you to understand:

```text
                 FLOW GROUP
             A → D, QoS = High
                     │
                     ▼
              TUNNEL GROUP
             /             \
            /               \
           ▼                 ▼
      Tunnel 1           Tunnel 2
      A → B → D          A → C → D
          │                  │
          ▼                  ▼
         60%                40%
```

Read it as:

> “For this particular Flow Group, send 60% of the traffic through Tunnel 1 and 40% through Tunnel 2.”

That's the basic mechanism behind B4's multipath traffic engineering.

---

# 6. Why is this better than simply choosing one path?

Suppose:

```text
A → B → D
```

has only 40 Gbps available.

But:

```text
A → C → D
```

has 100 Gbps available.

If normal routing sends everything through A → B → D, we may overload that path.

B4 can instead distribute traffic:

```text
A → B → D     40%
A → C → D     60%
```

The exact percentages are determined by the TE system; this example is just for understanding.

This allows B4 to use the available network capacity more efficiently.

The paper describes the TE goal as sharing bandwidth among competing applications, potentially using multiple paths. 

---

# 7. One more important concept: QoS

You saw this in the Flow Group:

```text
{source, destination, QoS}
```

Why does QoS matter?

Imagine two types of traffic:

```text
High Priority:
Critical service data

Low Priority:
Large background data copy
```

If the network becomes congested, you don't necessarily want both to receive exactly the same treatment.

B4 was designed around Google's ability to classify applications and use their relative priorities when allocating bandwidth. 

So the TE system can consider not only:

> “Where is the traffic going?”

but also:

> **“How important is this traffic?”**

---

# 8. The complete B4 decision process

Now connect what we've learned in the previous slides:

```text
Application traffic
       │
       ▼
   Flow Group
(source, dest, QoS)
       │
       ▼
   TE Server
       │
       │ chooses
       ▼
  Tunnel Group
       │
       ├───────────────┐
       ▼               ▼
   Tunnel 1         Tunnel 2
   60%               40%
       │               │
       └───────┬───────┘
               ▼
            Network
```

Then the resulting configuration is passed toward the SDN Gateway and site OpenFlow Controllers, which install the necessary rules in the switches.

# 10. Speaking script

“Now we come to the basic abstractions used by B4's Traffic Engineering system.

First is the Flow Group. A Flow Group is defined by the source site, destination site, and QoS. This allows B4 to aggregate traffic instead of optimizing every individual application separately.

Next is a Tunnel. A tunnel represents a site-level path through the network, such as A to B to D.

Finally, a Tunnel Group maps a Flow Group to multiple tunnels and assigns a weight to each tunnel. The weight represents the fraction of traffic that should use that tunnel.

For example, if a Flow Group has two available tunnels, B4 might assign 60 percent of the traffic to one tunnel and 40 percent to the other.

Therefore, Flow Groups identify the traffic, tunnels represent possible paths, and Tunnel Groups determine how the traffic is distributed across those paths.”

# 11. Professor Q&A

### Q: What is a Flow Group?

**Answer:**

A Flow Group aggregates traffic using the tuple:

**{source site, destination site, QoS}.** 

---

### Q: What is a tunnel in B4?

**Answer:**

A tunnel represents a **site-level path**, such as A → B → C. B4 implements tunnels using IP-in-IP encapsulation. 

---

### Q: What is a Tunnel Group?

**Answer:**

A Tunnel Group maps a Flow Group to multiple tunnels and assigns weights that specify what fraction of traffic should use each tunnel. 

---

### Q: Why doesn't B4 optimize every application individually?

**Answer:**

For scalability. B4 aggregates applications into Flow Groups rather than performing TE at individual-application granularity. 

---

### Q: What does the weight mean?

**Answer:**

It represents the **fraction of the Flow Group's traffic** that should be forwarded through a particular tunnel.

For example:

```text
Tunnel 1 = 70%
Tunnel 2 = 30%
```

means approximately 70% and 30% of that Flow Group's traffic should use those tunnels.
