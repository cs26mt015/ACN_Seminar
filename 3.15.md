# Slide 15 — B4 Failure Handling

Now we reach an **extremely important part of the paper**.

So far, B4 sounds great:

* centralized control
* multiple paths
* high utilization
* fast TE optimization

But there's an obvious question:

> **What happens when something fails?**

A production WAN cannot assume that every link, switch, or controller will always work.

The paper actually measures failure behavior in several different components. 

---

## 1. The failures B4 tested

The paper looks at failures involving:

```text
1. Single link
2. Encapsulation switch
3. Transit switch
4. OpenFlow Controller (OFC)
5. TE Server
```

And the measured traffic-loss times were very different.

### Remember these numbers:

| Failure              | Traffic loss |
| -------------------- | -----------: |
| Single link          |     **4 ms** |
| Encapsulation switch |    **10 ms** |
| Transit switch       |  **3300 ms** |
| OFC                  |     **0 ms** |
| TE Server            |     **0 ms** |



The **3.3-second transit-switch failure** is the surprising one.

---

# 2. Single-link failure — 4 ms

Imagine:

```text
       B
      / \
A ───   ─── D
      \ /
       C
```

Suppose the link:

```text
A → B
```

fails.

B4 has multiple paths available.

So traffic can move through another path:

```text
A → C → D
```

The measured loss was approximately:

> **4 ms**

That's very small.

The important lesson:

> **Having multiple paths gives B4 the ability to recover quickly from individual link failures.**

---

# 3. Encapsulation switch failure — 10 ms

Now suppose the switch at the beginning of a tunnel fails.

Remember:

```text
Source → Transit → Destination
```

The source is responsible for **encapsulation**.

If that switch fails:

```text
Encapsulation switch
       ↓
      FAIL
       ↓
Traffic must recover
```

The measured loss was:

> **10 ms**

Still relatively small. 

---

# 4. Transit switch failure — 3300 ms

Now we get the surprising result.

A **transit switch** failure caused approximately:

> **3300 ms = 3.3 seconds of loss**

That's dramatically larger.

Compare:

```text
Link failure             4 ms
Encapsulation switch    10 ms
Transit switch        3300 ms
```

Visually:

```text
4 ms     █
10 ms    ██
3300 ms  ███████████████████████████████
```

So why was this so much worse?

The paper's analysis shows that the problem was associated with the control/recovery path around the affected transit switch and the mechanisms needed to recognize and react to the failure. 

For your seminar, the important takeaway is:

> **B4's data-plane path could be resilient, but the control path could still introduce significant recovery delays.**

This becomes even more important in the real outage we'll study next.

---

# 5. OpenFlow Controller failure — 0 ms

This is a very interesting result.

If an **OpenFlow Controller (OFC)** fails:

```text
OFC
 ↓
FAIL
```

the measured traffic loss was:

> **0 ms**

Why?

Because the forwarding behavior already installed in the switches can continue operating.

This demonstrates an important principle:

> **The controller doesn't have to be alive for every packet to be forwarded.**

The controller programs the switches; it isn't sitting in the packet's path forwarding each packet.

That's exactly why we emphasized earlier:

```text
Controller ≠ packet forwarding
```

---

# 6. TE Server failure — 0 ms

Similarly, when the TE Server fails, the measured traffic loss was:

> **0 ms**

Again, this doesn't mean:

> "Nothing happens when the TE Server fails."

It means the **currently installed forwarding state can continue forwarding traffic**.

Meanwhile, another TE server can take over as master.

Remember from Slide 13:

```text
TE1 = Master
TE2 = Hot standby
TE3 = Hot standby
```

If TE1 fails:

```text
TE1 ❌
 ↓
TE2 becomes master
```

The paper reports that hot standby takeover could occur in less than 10 seconds. 

So:

> **Control-plane failure does not necessarily mean immediate data-plane traffic loss.**

That's an important SDN concept.

---

# 7. The big distinction: Control plane vs Data plane

This is a perfect place to reinforce a concept you already learned.

### Data plane

Actually forwards packets:

```text
Packet → Switch → Switch → Switch
```

### Control plane

Decides/configures how forwarding should happen:

```text
TE Server
    ↓
OFC
    ↓
Switch configuration
```

Therefore:

```text
Control component fails
        ↓
Existing forwarding state
may continue
        ↓
Packets can still flow
```

But:

```text
Network topology changes
        ↓
Existing forwarding state
may become incorrect
        ↓
Control system must react
```

That's where the real difficulty appears.

---

# 8. Why is the transit-switch result important?

This gives us a deeper lesson.

You might initially think:

> "B4 has centralized control, so recovery should be easy."

Not necessarily.

There are two separate questions:

### Question 1

**Can packets keep forwarding using existing state?**

Often yes.

### Question 2

**Can the network quickly discover the failure and install new correct state?**

That's harder.

So:

```text
Failure
  ↓
Detection
  ↓
Control-plane reaction
  ↓
New forwarding state
  ↓
Recovery
```

The entire chain matters.

A fast algorithm doesn't automatically mean fast failure recovery.

# 🧠 Professor Q&A

### Q1. Which failure caused the largest traffic loss?

> **Transit switch failure — approximately 3.3 seconds.**

---

### Q2. Why can the network continue forwarding when the TE Server fails?

> Because the switches already have forwarding state installed. The TE Server is responsible for computing/control decisions, not forwarding individual packets.

---

### Q3. Why did an OFC failure cause 0 ms loss?

> Existing forwarding rules can continue operating even if the controller becomes unavailable.

---

### Q4. Does 0 ms mean the system completely ignores the controller failure?

> No. It means there was no measured immediate traffic loss from the existing forwarding state. The control system still needs to recover so that future changes can be handled.

---

### Q5. Why is a transit-switch failure worse than a link failure?

A safe answer based on the paper is:

> **The transit-switch failure exposed a longer control/recovery path than the simple link-failure case, resulting in approximately 3.3 seconds of loss.**

Don't invent a more specific mechanism unless you are prepared to explain the exact outage sequence from the paper.

# ⭐ Very important connection to the next slide

There is a difference between:

### Controlled failure

```text
One link fails
      ↓
Network detects it
      ↓
Alternative path
      ↓
Fast recovery
```

and a **complex control-plane failure** where multiple network mechanisms interact.

And that's exactly what happened in one of B4's real production incidents.

The paper describes a planned maintenance operation where a **duplicate switch ID caused link flaps**, which triggered a chain of control-plane problems involving **IS-IS, OpenFlow, BGP, and TE**. 

That is probably the **most valuable story in the entire paper for your seminar**, because it lets you show that Google learned things from an actual failure rather than only from experiments.
