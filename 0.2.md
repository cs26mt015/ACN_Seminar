Good. Now let’s go one level deeper: **how routing actually works**, and then connect that directly to **B4, BGP, IS-IS, and ECMP**.

I’ll keep this as a learning lesson rather than jumping into presentation material yet.

---

# 1. Routing: the basic problem

Imagine this network:

```text
                 Router B
                /        \
               /          \
Computer A → Router A      Router D → Computer B
               \          /
                \        /
                 Router C
```

Computer A wants to reach Computer B.

There are multiple possible paths:

```text
Path 1:
A → Router A → Router B → Router D → B

Path 2:
A → Router A → Router C → Router D → B
```

The network needs some mechanism to decide:

> **Which path should the packet take?**

That's the routing problem.

---

# 2. Routing table

A router doesn't normally calculate the entire path from scratch for every packet.

It has a **routing table**.

A simplified example:

```text
Destination       Next Hop
--------------------------------
10.2.0.0/16       Router B
10.3.0.0/16       Router C
10.4.0.0/16       Router D
```

Suppose a packet arrives:

```text
Destination = 10.4.5.20
```

The router looks at its routing information and effectively determines:

```text
10.4.5.20
     ↓
10.4.0.0/16
     ↓
Next hop = Router D
```

Then forwarding takes place:

```text
Packet
  ↓
Router
  ↓
Routing information
  ↓
Next hop
  ↓
Outgoing interface
```

So the distinction we discussed earlier becomes concrete:

```text
ROUTING
"What should the network do?"

        ↓

ROUTING TABLE
"Destination X → next hop Y"

        ↓

FORWARDING
"Send this packet out interface Z."
```

---

# 3. But who creates the routing table?

This is where **routing protocols** enter.

A router can learn information about the network using routing protocols.

For B4, two important names you need to recognize are:

* **BGP**
* **IS-IS**

The B4 paper says Google wanted to continue supporting existing distributed routing protocols while introducing centralized Traffic Engineering. 

Don't try to memorize their complete operation yet.

For your B4 seminar, initially think:

```text
Routing protocols
       ↓
learn/distribute network reachability
       ↓
routing decisions
       ↓
forwarding
```

---

# 4. BGP — what should you know?

**BGP = Border Gateway Protocol.**

For now, your mental model should be:

> BGP is a routing protocol used to exchange reachability information between network domains.

A very simplified example:

```text
Network A
   │
   │ BGP
   ▼
Network B
   │
   │ BGP
   ▼
Network C
```

BGP is particularly important for **inter-domain routing**.

You don't need to become a BGP expert before understanding B4.

What matters for B4 is that B4 **didn't throw away existing routing protocols**.

The paper explains that B4 ran as a single autonomous system and used BGP/ISIS-based routing, with the SDN system needing to support these existing protocols for interoperability and gradual deployment. 

---

# 5. IS-IS — what should you know?

**IS-IS = Intermediate System to Intermediate System.**

For your current level, think of it as another routing protocol used to distribute topology/reachability information within a network.

Very simplified:

```text
          IS-IS
            ↓
   ┌────────┼────────┐
   ↓        ↓        ↓
Router A Router B Router C
```

Routers exchange information about the network.

They can then calculate paths through the topology.

You don't need the detailed IS-IS packet formats or internal algorithms right now.

For B4, remember:

> **BGP/IS-IS = existing distributed routing infrastructure.**

And:

> **B4's centralized TE was added on top of that infrastructure.**

That second statement is extremely important.

---

# 6. Why didn't B4 just replace routing completely?

This is one of the first **"Why?" questions a professor could ask.**

You might initially think:

> "If B4 has SDN and a centralized controller, why not just put everything into the central controller?"

The B4 authors considered that approach.

They could have built one centralized service combining routing and traffic engineering.

Instead, they chose to keep:

```text
Existing routing
       +
Centralized TE
```

as separate services.

The standard routing service came first, and centralized TE was subsequently deployed as an overlay. 

Why is that useful?

Because if the new TE system has a serious problem, B4 can disable TE and fall back to shortest-path forwarding.

The paper describes this isolation as a "big red button" for fault recovery. ([Computer Science][1])

So conceptually:

```text
                 B4 NETWORK
                     │
          ┌──────────┴──────────┐
          │                     │
      BASE ROUTING          CENTRAL TE
       BGP / IS-IS              │
          │                     │
          │                optimization
          │                     │
          └──────────┬──────────┘
                     ↓
                 Forwarding
```

This is a very important B4 design idea.

---

# 7. Now: shortest path

Suppose the network looks like this:

```text
             10
        A -------- B
        |          |
       5|          |5
        |          |
        C -------- D
             2
```

From A to D:

Path 1:

```text
A → B → D
10 + 5 = 15
```

Path 2:

```text
A → C → D
5 + 2 = 7
```

A shortest-path routing algorithm would choose:

```text
A → C → D
```

That's perfectly reasonable.

But here's the problem:

**Shortest path isn't necessarily the best way to use the entire network.**

---

# 8. This is where B4's problem becomes interesting

Imagine:

```text
                100 Gbps
        ┌───────────────────┐
        │                   │
        ▼                   │
Data Center A            Data Center B
        ▲                   │
        │                   │
        └───────────────────┘
                100 Gbps
```

Suppose the shortest path is already carrying huge traffic.

Another path has spare capacity.

A traditional shortest-path approach might continue putting traffic on the shortest path.

Conceptually:

```text
Shortest path:
████████████████████ 100%

Other path:
████                    20%
```

That's not necessarily an efficient use of expensive WAN capacity.

B4's objective is different.

It wants to consider:

* available capacity
* application demands
* application priority
* multiple paths
* changing traffic
* failures

The paper explicitly describes B4's TE as using multipath forwarding/tunneling and dynamically reallocating bandwidth when demand or network conditions change. 

---

# 9. ECMP — another important term

You will encounter **ECMP** in the B4 paper.

ECMP means:

> **Equal-Cost Multi-Path**

Suppose:

```text
             ┌── Router B ──┐
             │              │
Router A ────┤              ├── Router D
             │              │
             └── Router C ──┘
```

Suppose both paths have the same routing cost:

```text
A → B → D
A → C → D
```

Instead of using only one path, traffic can be distributed across them.

Very simplified:

```text
Traffic
  │
  ├────────→ Path 1
  │
  └────────→ Path 2
```

B4 uses a **custom variant of ECMP hashing** when distributing traffic across the multiple links making up a site-to-site connection. ([studylib.net][2])

---

# 10. But ECMP is NOT the same thing as B4's TE

This distinction is important.

### ECMP

Essentially:

> "I have multiple equal-cost paths; distribute traffic among them."

### B4 centralized TE

Much broader:

> "I have knowledge about traffic demands, priorities, available capacity and network conditions. How should I allocate bandwidth across multiple paths?"

So:

```text
ECMP
  ↓
Equal-cost path distribution


B4 TE
  ↓
Centralized traffic allocation
  ↓
Application demands
  +
Priority
  +
Capacity
  +
Failures
  +
Multiple paths
```

B4 actually uses ECMP as part of its implementation, but its centralized TE is solving a larger allocation problem. ([studylib.net][2])

---

# 11. The key problem B4 is solving

Let's simplify the entire situation.

### Traditional approach

```text
Network topology
      ↓
Distributed routing
      ↓
Shortest paths
      ↓
Forward traffic
```

### B4 approach

```text
Network topology
      +
Traffic demands
      +
Application priority
      +
Available capacity
      +
Failures
      ↓
Centralized Traffic Engineering
      ↓
Multiple paths / tunnels
      ↓
Forward traffic
```

That is the conceptual leap you need to understand before studying the B4 architecture.

---

# 12. And now SDN makes sense

Previously, "SDN" might have sounded like just a buzzword.

Now you can see why B4 wanted it.

B4 wants a software system that can have a broader view:

```text
                 CENTRAL TE
                     │
       ┌─────────────┼─────────────┐
       │             │             │
       ▼             ▼             ▼
   Demand A       Demand B      Demand C
       │             │             │
       └─────────────┼─────────────┘
                     ↓
              Compute allocation
                     ↓
              Program switches
                     ↓
                  Forwarding
```

The paper's architecture separates control from forwarding: network control software runs on servers, while OpenFlow-enabled switches execute forwarding decisions. 

---

# 13. One very important mental model

I want you to remember this diagram:

```text
                  CONTROL PLANE
        "What should the network do?"
                         │
                         │
              ┌──────────┴──────────┐
              │                     │
          Routing                 TE
        BGP / IS-IS        Demand / capacity /
                           priority / failures
              │                     │
              └──────────┬──────────┘
                         │
                         ▼
                  Forwarding rules
                         │
                         │
                  ───────┼───────
                         │
                         ▼
                    DATA PLANE
              "Actually move packets"
                         │
                    ┌────┴────┐
                    ▼         ▼
                 Switch     Switch
```

**Control plane:** makes/maintains decisions.

**Data plane:** actually forwards packets.

This separation is fundamental to understanding B4.

---

# 14. Where OpenFlow enters

Now the last piece:

```text
CONTROL PLANE
     │
     │ OpenFlow
     ▼
┌─────────────┐
│   Switch    │
│             │
│ Forwarding  │
│   Table     │
└─────────────┘
     │
     ▼
  Packets
```

In B4, the OpenFlow controller sends commands toward the switch's OpenFlow agent, which translates them into commands that configure forwarding-table entries. 

So now our complete picture is:

```text
             B4 CENTRAL CONTROL
                     │
          ┌──────────┴──────────┐
          │                     │
       Routing                  TE
     BGP / IS-IS         traffic allocation
          │                     │
          └──────────┬──────────┘
                     ▼
              SDN Controller
                     │
                  OpenFlow
                     │
                     ▼
              ┌─────────────┐
              │   Switch    │
              │ forwarding  │
              │    table    │
              └─────────────┘
                     │
                     ▼
                   PACKET
```

That is **the backbone of the B4 paper**.
