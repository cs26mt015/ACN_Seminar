Excellent. This is the **heart of B4**. If you understand this section, you’ll understand why B4 is a research paper rather than just an SDN deployment.

---

# 1. What is B4's TE trying to do?

Suppose several applications want bandwidth:

```text
App A ── wants ── 20 Gbps
App B ── wants ── 10 Gbps
App C ── wants ── 30 Gbps
```

But the network has limited capacity:

```text
          10 Gbps
     A ─────────── B
      \            /
       \ 20 Gbps  /
        \        /
         ────────
```

You cannot necessarily give everyone everything they want.

So B4 needs to answer:

> **Who gets how much bandwidth, and through which paths?**

The paper defines the TE objective as **max-min fair allocation** among competing applications, potentially using multiple paths. 

---

# 2. What does "max-min fair" mean?

Don't let the name scare you.

Imagine three people sharing water:

```text
Person A wants: 10 L
Person B wants: 20 L
Person C wants: 30 L

Available: 30 L
```

A simple fair approach might give:

```text
A = 10 L
B = 10 L
C = 10 L
```

A gets everything it needs, while B and C share the remaining capacity.

That's the basic intuition of **max-min fairness**:

> Don't give additional resources to one application if doing so would unfairly reduce the share available to another application that is still underserved.

B4 uses this idea while also considering **application priorities** through bandwidth functions.

---

# 3. B4 doesn't optimize individual applications directly

This is an important scalability decision.

Imagine Google has thousands of applications.

The TE system cannot realistically optimize:

```text
App 1
App 2
App 3
...
App 100000
```

individually.

So B4 groups applications into something called a:

## Flow Group (FG)

A Flow Group is defined by:

```text
{source site, destination site, QoS}
```



For example:

```text
FG1 = {Data Center A → Data Center B, QoS X}
FG2 = {Data Center A → Data Center C, QoS Y}
```

So instead of thinking:

```text
Application 1
Application 2
Application 3
Application 4
```

TE thinks more like:

```text
        Applications
        /    |    \
       /     |     \
      ▼      ▼      ▼
    ┌─────────────────┐
    │   FLOW GROUP    │
    └─────────────────┘
```

This dramatically reduces the problem size.

---

# 4. Next concept: Tunnel

Suppose we have:

```text
A ─── B ─── C
```

A tunnel can represent the site-level path:

```text
A → B → C
```

The paper defines a tunnel as a **site-level path**, such as `A → B → C`. B4 implements these tunnels using IP-in-IP encapsulation. 

So:

```text
Tunnel 1:
A → B → C
```

could be one possible route.

Another could be:

```text
Tunnel 2:
A → D → C
```

---

# 5. Tunnel Group

Now suppose FG1 has three possible tunnels:

```text
FG1

Tunnel 1: A → B → C
Tunnel 2: A → D → C
Tunnel 3: A → E → F → C
```

B4 can split traffic among them.

For example:

```text
Tunnel 1 → 50%
Tunnel 2 → 30%
Tunnel 3 → 20%
```

That collection is a:

## Tunnel Group (TG)

The paper defines a Tunnel Group as mapping a Flow Group to a set of tunnels and corresponding weights. The weight represents the fraction of that Flow Group's traffic sent along each tunnel. 

So:

```text
             FG1
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
      T1      T2     T3
      │       │      │
     50%     30%    20%
```

This is one of the most important diagrams to understand.

---

# 6. So now we have three terms

Memorize this relationship:

```text
FLOW GROUP
    │
    │ gets
    ▼
TUNNEL GROUP
    │
    ├──── Tunnel 1
    ├──── Tunnel 2
    └──── Tunnel 3
```

And:

```text
FG = WHO is communicating

Tunnel = WHICH path

Tunnel Group = HOW traffic is split across those paths
```

That's an excellent mental shortcut.

---

# 7. Now comes the interesting part: bandwidth functions

B4 doesn't treat every application equally.

Suppose:

```text
App A = high priority
App B = medium priority
App C = low priority
```

B4 represents their relative priority using **bandwidth functions**.

The paper describes a bandwidth function as effectively a contract between an application and B4, specifying bandwidth allocation based on a dimensionless "fair share." 

You don't need the mathematical graph yet.

Think of it as:

```text
Fair Share
     │
     ▼
Bandwidth allocated to application
```

---

# 8. Different applications can have different priorities

The paper gives this example:

```text
App1 → weight 10
App2 → weight 1
App3 → weight 0.5
```



So if resources become scarce, App1's bandwidth function grows much faster than App3's.

Conceptually:

```text
Priority

App1  ██████████
App2  █
App3  ▌
```

This doesn't mean:

> "App1 always gets everything."

It means B4 incorporates relative application priority into the fairness calculation.

---

# 9. Now let's solve B4's example

This is where the paper gets mathematical, but we'll make it intuitive.

The example has four sites:

```text
        B
       / \
      /   \
     A     C
      \   /
       \ /
        D
```

There are two Flow Groups:

```text
FG1: A → B
Demand = 20 Gbps

FG2: A → C
Demand = 10 Gbps
```

The paper gives edge costs, with most edges having cost 1 and A→D having cost 10. 

The algorithm tries to allocate bandwidth while respecting:

* demand
* priority
* edge capacity
* available paths
* fairness

---

# 10. Step 1 — Start with preferred paths

Initially:

```text
FG1:
A → B

FG2:
A → C
```

These are their preferred/lowest-cost paths.

So:

```text
             FG1
              │
              ▼
A ──────────── B


             FG2
              │
              ▼
A ──────────── C
```

The algorithm begins increasing the fair share of the Flow Groups.

---

# 11. Step 2 — Find a bottleneck

Eventually an edge becomes full.

The paper's example reaches a fair share of **0.9**, where:

```text
FG1 → 10 Gbps
FG2 → 0.45 Gbps
```

At this point, the A→B edge becomes full.

That edge is called the:

## Bottleneck edge



Think:

```text
A ═══════════ B
      FULL
       ❌
```

The algorithm now says:

> "I can't send any more traffic through this edge."

So it freezes the tunnel using that bottleneck.

---

# 12. Step 3 — Find another path

FG1 still wants more bandwidth.

Its first path is blocked.

So B4 looks for its next preferred tunnel:

```text
A → C → B
```

Now:

```text
FG1
 │
 ├── T1: A → B        ❌ full
 │
 └── T2: A → C → B    ← try this
```

At this point the algorithm can continue allocating bandwidth.

---

# 13. Another bottleneck appears

The algorithm eventually finds that:

```text
A → C
```

becomes the next bottleneck.

So:

```text
A ═════════ C
      FULL
       ❌
```

Again, the algorithm freezes paths crossing that edge.

FG1 is forced to its next preferred path:

```text
A → D → C → B
```

And FG2 also moves to another path.

The important idea isn't memorizing every number.

It's this:

```text
Preferred path
      ↓
Becomes bottleneck
      ↓
Freeze it
      ↓
Find another path
      ↓
Continue allocating
      ↓
Another bottleneck
      ↓
Find another path
```

That's the core of the algorithm.

---

# 14. The final allocation

For the paper's example, the resulting allocation before hardware quantization is:

### FG2

```text
Tunnel 1 → 30%
Tunnel 2 → 70%
```

### FG1

```text
Tunnel 1 → 50%
Tunnel 2 → 40%
Tunnel 3 → 10%
```



So instead of:

```text
FG1 → one path
```

B4 can do:

```text
             FG1
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
      T1     T2     T3
     50%    40%    10%
```

This is **multipath traffic engineering**.

---

# 15. Why doesn't B4 just calculate the mathematically perfect answer?

Excellent question.

The paper says an exact **linear-programming (LP)** solution for the allocation problem is expensive and doesn't scale well.

So the authors designed their own algorithm.

Their algorithm achieved:

* similar fairness
* at least **99% of the bandwidth utilization**
* approximately **25× faster performance** than the LP approach for their deployment



This is an important research contribution.

It's not just:

> "We used SDN."

It's:

> **"We designed a scalable TE algorithm that gets close to the ideal solution much faster."**

That's the kind of statement that will matter when we later discuss what the actual research contribution of B4 was.

---

# 16. The algorithm has TWO major parts

The paper explicitly divides the TE optimization algorithm into:

### 1. Tunnel Group Generation

Decides:

```text
How much bandwidth
should each Flow Group receive?
```

and:

```text
Which tunnels should carry it?
```

### 2. Tunnel Group Quantization

Takes those ideal split ratios and changes them into ratios that the actual switch hardware can support.



So:

```text
          TE Optimization
                 │
        ┌────────┴────────┐
        ▼                 ▼
Tunnel Group          Tunnel Group
Generation            Quantization
        │                 │
        ▼                 ▼
Ideal allocation     Hardware-compatible
                     allocation
```

---

# 17. Why do we need quantization?

Suppose the ideal algorithm says:

```text
Tunnel A = 37%
Tunnel B = 63%
```

But the hardware might only support certain granularities.

So B4 has to convert the ideal answer into something the switch can actually implement.

The paper's example uses splits in multiples of **0.5**. 

Conceptually:

```text
Ideal:

37% / 63%

       ↓

Hardware constraints

       ↓

40% / 60%
```

The actual paper's example is more detailed, but this is the intuition.

---

# 18. So what does the whole TE pipeline look like?

Now we can connect everything:

```text
Applications
     │
     ▼
Bandwidth functions
     │
     ▼
Flow Groups
     │
     ▼
TE Optimization
     │
     ├── Tunnel Group Generation
     │
     └── Tunnel Group Quantization
     │
     ▼
Tunnel Groups
     │
     ▼
SDN Gateway
     │
     ▼
OpenFlow Controllers
     │
     ▼
Switches
```

This is the **central brain of B4**.

# 19. But how does a packet actually use these tunnels?

This is the next important step.

Suppose:

```text
FG1
```

has:

```text
T1 = 50%
T2 = 50%
```

A packet arrives at the source site.

The switch identifies that the packet belongs to FG1.

Then it hashes the packet to determine which tunnel it should use.

So:

```text
Packet 1 ──→ T1
Packet 2 ──→ T2
Packet 3 ──→ T1
Packet 4 ──→ T2
```

The paper says incoming packets matching a Flow Group are forwarded through the corresponding Tunnel Group, with each packet hashed to one of the associated tunnels according to the desired ratio. 

---

# 20. Why tunnels?

Here's the clever implementation.

Suppose the normal packet is:

```text
Source = A
Destination = B
```

B4 can encapsulate it with an **outer IP header** identifying the tunnel.

Conceptually:

```text
Original packet
┌───────────────────────┐
│ A → B                 │
└───────────────────────┘

          ↓ encapsulate

┌────────────────────────────────┐
│ Outer: Tunnel ID               │
│ Inner: Original A → B packet   │
└────────────────────────────────┘
```

The transit switches don't need to understand the original application flow.

They can simply look at the outer tunnel information and forward accordingly.

---

# 21. The three switch roles

This is another thing worth remembering.

B4 switches can have three roles:

### 1. Encapsulating switch

Starts the tunnel.

```text
Original packet
      ↓
Encapsulate
      ↓
Tunnel
```

### 2. Transit switch

Carries the tunnel.

```text
Tunnel packet
      ↓
Look at outer header
      ↓
Forward
```

### 3. Decapsulating switch

Ends the tunnel.

```text
Tunnel packet
      ↓
Remove outer header
      ↓
Original packet
      ↓
Normal forwarding
```

The paper explicitly defines these three roles.

# 23. The most important conceptual distinction

Don't confuse these:

```text
ROUTING
    ↓
"What paths exist / what is the baseline route?"

TE
    ↓
"How should I allocate traffic across those paths?"

OPENFLOW
    ↓
"How do I program the switch to implement the decision?"

TUNNEL
    ↓
"How is that chosen path represented and carried?"

ECMP/HASHING
    ↓
"How do I distribute individual flows across the selected paths?"
```

If you understand that chain, you're in very good shape for the paper.
