# Slide 11 — How Does a B4 Tunnel Carry a Packet?

Now we move from **"what path did B4 choose?"** to:

> **"How does a packet actually travel through that chosen tunnel?"**

This is important because the word **tunnel** can sound abstract.

In B4, tunnels are implemented using **IP-in-IP encapsulation**. 

---

## 1. First, remember our example

Suppose B4 has:

```text
Source site = A
Destination site = D
```

And the TE system selected:

```text
Tunnel 1:
A → B → D
```

So logically:

```text
A ─────→ B ─────→ D
```

But the original packet is not necessarily addressed specifically to B.

B4 needs a way to make the packet follow the selected tunnel.

That's where **encapsulation** comes in.

---

# 2. What is IP-in-IP encapsulation?

Very simply:

> **B4 puts the original IP packet inside another IP packet.**

Think of it like putting a letter inside another envelope.

```text
Outer IP header
        +
Original IP packet
```

Conceptually:

```text
┌─────────────────────────────┐
│ Outer IP Header             │
│   A → B                     │
├─────────────────────────────┤
│ Original IP Packet          │
│   Original Source → D       │
│   Original Destination → D  │
└─────────────────────────────┘
```

The **outer header** is used to move the packet through the tunnel.

The **original packet** remains inside.

---

# 3. Three roles in a tunnel

The paper describes three important roles.

### ① Source / Encapsulating switch

At the beginning:

```text
A
│
│ Add outer IP header
↓
[Outer packet + Original packet]
```

The source switch **encapsulates** the packet.

---

### ② Transit switch

The packet travels through intermediate sites.

For example:

```text
A ─────→ B ─────→ D
          ↑
       Transit
```

The transit switch sees the **outer header** and forwards the packet according to that outer destination.

It doesn't need to understand the original application's packet in order to move it through the tunnel.

---

### ③ Destination / Decapsulating switch

When the packet reaches D:

```text
D
│
│ Remove outer header
↓
Original IP packet
```

The destination switch **decapsulates** the packet.

Then normal routing/forwarding can continue.

This source → transit → destination model is described in the paper's tunnel implementation discussion. 

---

# 4. Full example

Let's follow one packet.

Suppose:

```text
Original packet:

Source = Server A1
Destination = Server D1
```

B4 has decided that this traffic should use:

```text
A → B → D
```

### Step 1 — Source switch

The source switch adds an outer IP header:

```text
┌─────────────────────────────┐
│ Outer: A → B/D tunnel path  │
├─────────────────────────────┤
│ Original: A1 → D1           │
└─────────────────────────────┘
```

Now the network can forward using the tunnel information.

---

### Step 2 — Transit

At B:

```text
        Outer header
             ↓
A ─────────→ B ─────────→ D
             │
        forward packet
```

B forwards the encapsulated packet toward D.

---

### Step 3 — Destination

At D:

```text
┌─────────────────────────────┐
│ Outer header                │ ← removed
├─────────────────────────────┤
│ Original packet A1 → D1     │
└─────────────────────────────┘
```

The outer header is removed.

The original packet is then handled normally.

---

# 5. Why does B4 need tunnels?

This connects directly to everything we've learned.

Remember:

### Routing

```text
What paths are available?
```

### TE

```text
How should traffic be distributed?
```

### Tunnel

```text
How do we represent/carry one of those
chosen site-to-site paths?
```

So:

```text
Routing
   ↓
Available paths

TE
   ↓
Choose/use paths

Tunnel
   ↓
Carry traffic along selected path
```

This is why **Tunnel** is an important B4 concept.

---

# 6. Very important: Tunnel ≠ physical cable

A professor may ask this.

Suppose we have:

```text
A ── B ── C ── D
```

A B4 tunnel:

```text
A → B → C → D
```

doesn't necessarily mean:

> "There is one special physical cable connecting A to B to C to D."

Instead, the tunnel is a **logical path implemented through the network**.

The underlying physical network still contains links and switches.

So:

```text
Logical:
A ───────→ B ───────→ D

Physical:
many physical links/switches underneath
```

This is one of the benefits of separating the logical TE view from the physical forwarding infrastructure.

# 🎤 Speaking script

You can say:

> "We have seen that B4's traffic engineering system chooses tunnels. But how is a tunnel actually implemented?
>
> B4 uses IP-in-IP encapsulation. The source switch adds an outer IP header around the original packet. This outer header allows the packet to travel through the selected tunnel.
>
> Intermediate switches forward the encapsulated packet using the outer header. Finally, at the destination site, the destination switch removes the outer header and the original packet continues through normal forwarding.
>
> So conceptually, a B4 tunnel has three roles: the source encapsulates, the transit switches forward, and the destination decapsulates."

# 🧠 Professor Q&A

### Q1. What is IP-in-IP encapsulation?

> It means placing an IP packet inside another IP packet by adding an outer IP header.

### Q2. Why add another IP header?

> The outer header provides the information needed to carry the original packet through the selected tunnel.

### Q3. What does the transit switch do?

> It forwards the encapsulated packet using the outer header.

### Q4. What happens at the destination?

> The destination switch removes the outer header, or decapsulates the packet, and the original packet continues through normal forwarding.

### Q5. Is a B4 tunnel a physical link?

> No. It is a logical path through the network implemented using forwarding and encapsulation.
