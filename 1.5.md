This is the **most important section for your seminar after the architecture** because now we can answer:

> **Did B4 actually work in Google's production network?**

Yes—the paper evaluates the deployed system and reports its operational experience, performance, utilization, and failure behavior. 

# 1. B4 was actually deployed

This isn't just a simulation or theoretical proposal.

The authors report their **deployment and operational experience with B4**. They also evolved the system after deployment. 

One interesting fact:

> B4 traffic roughly **doubled during 2012**.

And the authors say they were able to deploy new functionality, such as centralized TE, on top of their existing SDN framework. 

---

# 2. B4's scale

The paper gives a snapshot of the system from **September–November 2012**.

| Metric                  |          B4 |
| ----------------------- | ----------: |
| Sites                   |      **16** |
| Unidirectional edges    |      **46** |
| Tunnel Groups           |     **240** |
| Flow Groups             |   **2,700** |
| Tunnels in use          |     **350** |
| Cached tunnels          |   **1,150** |
| Topology changes        | **286/day** |
| Edge additions/removals |   **7/day** |



### Why does this matter?

It shows we're not talking about a tiny experimental network.

There are:

```text
16 sites
 ↓
46 edges
 ↓
2700 flow groups
 ↓
350 active tunnels
```

So B4 had to operate at meaningful scale.

---

# 3. The TE algorithm itself was fast

The paper reports:

```text
Average daily runs: 540
Average runtime:    0.3 seconds
Maximum runtime:    0.8 seconds
```



That's important because remember our earlier discussion:

> B4's TE algorithm has to repeatedly calculate how traffic should be distributed.

It can't take minutes to calculate a new configuration when network conditions change.

---

# 4. Why topology aggregation matters

The B4 TE system doesn't treat every physical link as a completely separate global object.

It uses an aggregated topology view.

The paper reports:

```text
286 topology changes/day
```

but only:

```text
7 edge additions/removals/day
```

in the aggregated topology. 

So conceptually:

```text
Many physical changes
        ↓
Topology aggregation
        ↓
Fewer changes visible to TE
        ↓
Less TE processing / fewer operations
```

The authors identify this as one of the main benefits of topology aggregation.

---

# 5. B4 also had redundancy in the TE servers

The system used:

```text
5 geographically distributed TE servers
```

They participated in master election.

The secondary servers were **hot standbys** and could take over mastership in **less than 10 seconds**. The master typically remained stable for about **11 days** on average. 

So:

```text
          TE Servers
       ┌────┬────┬────┬────┬────┐
       │ S1 │ S2 │ S3 │ S4 │ S5 │
       └────┴────┴────┴────┴────┘
                │
             Master
                │
        ┌───────┴───────┐
        │               │
      Active          Standby
```

If the master fails, another server can take over.

---

# 6. But programming the switches was not free

Here's an important limitation.

The TE algorithm itself was fast.

But **actually programming the switches could take significant time**.

The paper measured the latency of TE operations and found that a substantial fraction of the time could be spent in switch programming. 

The paper gives these switch-time fractions:

| TE operation latency | Average switch-time fraction |
| -------------------- | ---------------------------: |
| 0–1 s                |                         0.40 |
| 1–3 s                |                         0.55 |
| 3–5 s                |                         0.71 |
| >5 s                 |                         0.77 |



Meaning that for slower operations, a large fraction of the total time was spent interacting with the switches.

---

# 7. Why was this a problem?

Remember the architecture:

```text
TE Server
    ↓
SDN Gateway
    ↓
OFC
    ↓
OFA
    ↓
Switch hardware
```

The paper says OpenFlow-style dynamic table programming was still relatively early, and the software and switch SDKs weren't optimized for frequent dynamic programming. 

So B4 exposed an important practical lesson:

> **Having a centralized control algorithm isn't enough. The underlying switch-programming mechanism also needs to be fast.**

That's a very good Q&A point.

# 8. Now the interesting part: failures

The researchers tested several failure scenarios.

They measured packet loss during:

1. Single link failure
2. Encapsulation switch failure
3. Transit switch failure
4. OFC failover
5. TE server failover
6. Disabling/enabling TE

The results are:

| Failure                                         | Packet loss |
| ----------------------------------------------- | ----------: |
| Single link                                     |    **4 ms** |
| Encapsulation switch                            |   **10 ms** |
| Transit switch neighboring encapsulation switch | **3300 ms** |
| OFC                                             |    **0 ms** |
| TE Server                                       |    **0 ms** |
| TE disable/enable                               |    **0 ms** |



These numbers are **excellent seminar material** because they show both strengths **and** weaknesses.

---

# 9. Why was a single link failure only 4 ms?

B4's affected switches quickly remove the failed link from their ECMP groups.

So:

```text
Before:

A ── Link 1 ──► B
A ── Link 2 ──► B


Link 1 fails

        X
A ── Link 1 ──► B

A ── Link 2 ──► B
        ↑
     continue
```

The paper reports only about **4 ms** of traffic loss for a single-link failure. 

---

# 10. But a transit-switch failure was much worse

This is one of the most interesting results.

A transit switch failure neighboring an encapsulation switch caused about:

**3.3 seconds of traffic loss.**

Why?

Because the encapsulation switch might have multiple tunnels passing through that failed transit switch.

It therefore needs to update its multipath table entries.

And the paper says each such operation was typically around **100 ms**. 

So:

```text
Transit switch fails
        ↓
Multiple tunnels affected
        ↓
Encap switch must modify multipath state
        ↓
Switch programming is slow
        ↓
~3.3 sec loss
```

This is a **real limitation** of the deployed system.

---

# 11. The software failures were surprisingly clean

OFC failure:

```text
0 ms
```

TE Server failure:

```text
0 ms
```

And disabling/enabling TE:

```text
0 ms
```

The authors describe OFC and TE server failover/restart as **hitless**, meaning that, absent additional concurrent failures, the data plane continues forwarding traffic. 

Why?

Because forwarding state already exists in the switches.

The data plane doesn't necessarily need the controller to be alive every moment.

That's an important SDN concept.

---

# 12. What happens if TE itself is disabled?

Remember the fallback mechanism we learned earlier?

It becomes important here.

When TE is disabled:

```text
B4 TE rules
     ↓
disabled
     ↓
baseline routing rules
     ↓
normal forwarding
```

The paper reports **0 ms traffic loss** for TE disable/enable in their experiment and says traffic falls back to the lower-priority forwarding rules established by the baseline routing protocol. 

So this isn't just an architectural idea—the authors actually evaluated it.

---

# 13. Did TE actually improve throughput?

Yes.

The authors compared B4 TE against **shortest-path routing** using production flow data.

They found that:

> B4 TE provided a **14% average throughput increase**.



But there's an important nuance.

The authors explain that the biggest benefit isn't necessarily the average throughput number.

The major benefit comes during:

* high-demand periods
* failures
* large transfers

For example, they describe a weekly high-priority data copy that requires half the capacity of a shortest path. Moving it to an alternate path only improves average weekly utilization by 5%, but can reduce required deployed WAN capacity by a factor of **2**. 

That's a powerful result.

---

# 14. Why does using more paths help?

The paper evaluated how throughput changes as the TE algorithm gets more possible paths.

Conceptually:

```text
1 path
   ↓
2 paths
   ↓
3 paths
   ↓
4 paths
```

Throughput improves as more paths become available, but the improvement starts to flatten around **4 paths**. 

There is a trade-off:

```text
More paths
    ↓
More flexibility
    ↓
Better traffic distribution

BUT

More paths
    ↓
More hardware table resources
```

The paper therefore uses:

**4 paths**

in deployment.

---

# 15. What about the path split granularity?

Remember quantization?

For example:

```text
Tunnel A = 50%
Tunnel B = 50%
```

The hardware can only support certain split ratios.

The paper evaluated different split granularities and found throughput improvements flatten around a **1/16 quantum**. For deployment, they use a **1/4 quantum and 4 paths**. 

So again:

```text
Finer split
    ↓
More flexibility
    ↓
Potentially better throughput

BUT

Finer split
    ↓
More hardware resources
```

B4 chooses a practical compromise.

---

# 16. Now the big B4 result: utilization

This is probably the **single most important result** of the paper.

Traditional WANs often operate around:

```text
30–40% utilization
```

because operators want spare capacity for failures and traffic bursts.

B4 instead pushes its busiest links toward:

```text
~100% utilization
```

The paper says the busiest B4 edges constantly run near 100%, and almost all links reach full utilization during the day. 

---

# 17. "But wouldn't 100% utilization cause packet loss?"

Excellent question.

B4 handles this using **traffic priorities**.

Think:

```text
High-priority traffic
        ↓
Must be protected

Low-priority traffic
        ↓
Can tolerate some loss
```

The centralized TE system mixes the priority classes across links.

Low-priority traffic can use the remaining capacity aggressively, while local QoS mechanisms protect high-priority traffic. 

So:

```text
WAN link
████████████████████  ~100%

High priority → protected
Low priority  → absorbs congestion/loss
```

And low-priority applications can throttle their transmission rate according to available capacity. 

---

# 18. Load balancing was also important

Remember that B4 abstracts physical links into larger logical site-to-site edges.

For that abstraction to work, traffic needs to be balanced across the underlying physical links.

The paper reports:

* For at least **75% of site-to-site edges**
* max:min link-utilization ratio was **1.05 without failures**
* and **2.0 with failures**. 

So without failures:

```text
Link 1 → 95%
Link 2 → 100%
Link 3 → 97%
Link 4 → 98%
```

is much better than:

```text
Link 1 → 100%
Link 2 → 100%
Link 3 → 20%
Link 4 → 10%
```

This validates the hashing/load-balancing approach we learned earlier.

# 19. And then comes the most valuable part: the outage

The paper doesn't hide a major outage.

The authors say B4 experienced **one substantial outage**, which taught them important lessons about operating a large WAN and SDN system. 

This is actually great for your seminar.

A research paper becomes more interesting when it says:

> "Here is what worked—and here is what broke."

---

# 20. What caused the outage?

During planned maintenance, one new switch was accidentally configured with the **same ID as an existing switch**.

That caused substantial link flaps.

Then ISIS began generating and flooding conflicting topology information.

This created heavy protocol processing. 

The chain became:

```text
Duplicate switch ID
       ↓
ISIS topology problems
       ↓
Many LSPs
       ↓
Huge queue buildup
       ↓
Delayed ISIS Hello messages
       ↓
Interfaces declared down
       ↓
BGP adjacencies break
       ↓
OFC/control-plane problems
       ↓
Large outage
```

The OFC-to-OFA path became a bottleneck, with queues growing beyond **400 MB** at the peak. 

---

# 21. What did the authors learn?

The outage produced several lessons, including:

### 1. Control-path scalability matters

The packet/control path between OFC and OFA needs to be fast enough.

### 2. OFA should be more asynchronous and parallel

Switch programming shouldn't unnecessarily happen serially.

### 3. Performance needs to be measured near the breaking point

Systems should be stress-tested before they reach production limits.

### 4. Control-plane failure doesn't automatically invalidate forwarding state

Existing TE forwarding state can continue operating even if the control connection is lost.

### 5. Human error matters

Large complex systems are vulnerable to configuration mistakes.

The authors argue that SDN offers an opportunity to simplify operations and reduce manual multi-step configuration.
