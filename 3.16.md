# Slide 16 — The Real B4 Production Outage

This is one of the **most valuable slides in your seminar**.

Why?

Because now you're not saying:

> "B4 handles failures."

You're showing:

> **"Here is what actually happened when a real production failure occurred."**

The paper describes a planned maintenance operation that triggered an unexpected chain of control-plane failures. 

---

## 1. It started with a human/operational mistake

During planned maintenance, a **duplicate switch ID** was introduced.

Think of it simply as:

```text
Switch A → ID = 100

Switch B → ID = 100   ❌
```

Two switches were using the same identifier when they should have had unique identities.

This caused **link flapping**.

### Link flapping

A link repeatedly appears to:

```text
UP → DOWN → UP → DOWN → ...
```

Instead of remaining stable.

And that triggered the next problem.

---

# 2. Link flapping caused IS-IS problems

Remember:

> **IS-IS is part of B4's traditional routing system.**

When the topology changes, IS-IS distributes information about those changes.

The repeated link changes caused **IS-IS LSP flooding and processing**.

Think of LSPs here as routing information being distributed through the network.

The chain started becoming:

```text
Duplicate switch ID
        ↓
Link flapping
        ↓
IS-IS changes
        ↓
LSP flooding
        ↓
More control traffic
```

This is important because a small operational mistake was beginning to create a much larger control-plane problem.

---

# 3. The control path became congested

Now remember something we learned earlier:

B4 has a control path connecting the network devices and controllers.

During the incident, the **OpenFlow Controller (OFC) to OpenFlow Agent (OFA) path became constrained**, and a queue grew beyond **400 MB**. 

Conceptually:

```text
Normal:

OFC ─────────────→ OFA


During incident:

OFC ─────────────→ OFA
       │
       │
       └── huge queue
           > 400 MB
```

So now control messages were delayed.

This is a crucial lesson:

> **The network can have enough capacity for normal data traffic but still have problems in the control path.**

---

# 4. IS-IS Hellos became delayed

IS-IS uses **Hello messages** to maintain neighbor relationships.

Because the control path was under stress, these Hellos were delayed.

Eventually:

```text
Expected Hello
      ↓
Delayed
      ↓
Another Hello delayed
      ↓
Neighbor appears unreachable
```

The interfaces were eventually considered down.

---

# 5. BGP adjacencies broke

Now another protocol was affected.

Remember:

```text
BGP
 ↓
Routing reachability
```

Because the interfaces were considered down, **BGP adjacencies broke**.

So the chain became:

```text id="x5t0qi"
Duplicate switch ID
        ↓
Link flapping
        ↓
IS-IS LSP flooding
        ↓
Control-path congestion
        ↓
Delayed IS-IS Hellos
        ↓
Interfaces go down
        ↓
BGP adjacencies break
```

One small operational problem had now propagated through multiple networking mechanisms.

---

# 6. What happened to B4's TE traffic?

Here's the interesting part.

The existing **TE transit traffic continued using the last known state**.

So B4 wasn't immediately saying:

> "Everything is broken; stop all traffic."

Instead, existing transit forwarding could continue.

But there was another problem:

### New tunnels could not be created.

Why?

Because the underlying control/routing state was no longer healthy enough to establish them.

So:

```text
Existing TE traffic
       ↓
Could continue
       ↓
Last known state
```

but:

```text
New tunnel required
       ↓
Control system needed
       ↓
Control path unhealthy
       ↓
New tunnel creation failed
```

This distinction is extremely important.

---

# 7. Operators had to intervene

At this point, Google operators took action.

The paper describes the operators:

### 1. Draining the affected site

They moved traffic away from the problematic site.

Conceptually:

```text
Problematic site
      ↓
Drain traffic
      ↓
Reduce impact
```

### 2. Disable TE

They used the B4 fallback mechanism:

> **Disable TE and return to normal routing behavior.**

Remember the **"big red button"** we discussed earlier.

```text
B4 TE
  ↓
DISABLE
  ↓
Normal shortest-path forwarding
```

### 3. Restart OFCs

The OpenFlow Controllers were restarted to recover the control system.

# 9. What did Google learn?

This is where you should transition from:

**"What happened?"**

to:

**"What does this teach us?"**

The paper identifies several lessons from the incident.

### Lesson 1 — Control-path scalability matters

It isn't enough for the data network to have lots of bandwidth.

The control system also has to handle bursts of control traffic.

---

### Lesson 2 — Control operations need to be efficient

The paper discusses improving the OFA through more asynchronous/multithreaded behavior and profiling.

The goal is to prevent control operations from becoming a bottleneck.

---

### Lesson 3 — Distinguish different types of failures

A hardware failure and a control-path failure may look very different.

The system needs to understand:

```text
Hardware problem?
        vs
Control-plane problem?
```

because the recovery strategy may differ.

---

### Lesson 4 — TE should adapt to unresponsive OFCs

If an OpenFlow Controller becomes unresponsive, the TE system should be able to recognize that and react appropriately rather than continuing as if everything were healthy.

---

### Lesson 5 — Human errors matter

This outage didn't begin with some exotic mathematical problem.

It began with:

> **a duplicate switch ID during planned maintenance.**

Production systems therefore need:

* validation
* safeguards
* stress testing
* operational discipline

# 🧠 Professor Q&A

### Q1. What caused the outage?

> A **duplicate switch ID during planned maintenance** caused link flapping, which triggered a chain of control-plane problems.

---

### Q2. Why did BGP break?

> The control-plane problems delayed IS-IS Hello messages, causing interfaces to be considered down, which led to BGP adjacencies breaking.

---

### Q3. Did all TE traffic immediately stop?

> No. Existing TE transit traffic continued using its last known state, but **new tunnels could not be created**.

---

### Q4. What did operators do?

> They **drained the affected site, disabled TE, and restarted the OpenFlow Controllers**.

---

### Q5. What was the biggest lesson?

A strong answer:

> **A centralized SDN system must scale and remain responsive not only in the data plane, but also in its control path.**

---

### Q6. Was B4 a failure because this outage happened?

**Don't answer "yes."**

A better answer:

> **The outage exposed weaknesses in the control path, but that's precisely why this paper is valuable: it reports the operational lessons and the improvements Google identified from running B4 in production.**

That is a much stronger research-paper answer.
