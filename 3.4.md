# ⭐ Now introduce the real problem

This is the most important part of this slide.

Imagine:

```text id="zvjqm8"
          A
         / \
        /   \
       B     C
        \   /
         \ /
          D
```

Suppose A needs to send a huge amount of traffic to D.

There are two possible paths:

```text id="m8rj91"
A → B → D

A → C → D
```

A traditional routing system may select paths based primarily on routing metrics.

But what if:

```text id="b0e4f6"
A → B → D
████████████████████  overloaded

A → C → D
████                  lightly used
```

Then simply choosing a path isn't enough.

We need to ask:

> **"How much traffic should use each path?"**

That's **Traffic Engineering**.

The B4 paper explicitly defines its TE goal as sharing bandwidth among competing applications, potentially using multiple paths. 

---

# 🧠 Routing vs Traffic Engineering

This distinction is **extremely important for your seminar**.

You should memorize this:

### Routing asks:

> **"Which paths are available?"**

### Traffic Engineering asks:

> **"How should I distribute traffic across those paths?"**

Example:

```text id="gk5n1q"
Available:

Path 1 ──────────►
Path 2 ──────────►
Path 3 ──────────►
```

Routing:

```text
These paths exist.
```

Traffic Engineering:

```text
Path 1 → 50%
Path 2 → 30%
Path 3 → 20%
```

This distinction will become **very important later** when we discuss B4's Tunnel Groups.

# ⭐ One excellent B4 design decision

There is another detail worth mentioning briefly.

B4 did **not** throw away traditional routing.

It kept standard routing protocols and layered centralized Traffic Engineering on top.

The paper says B4 deployed routing and TE as independent services, with TE subsequently deployed as an overlay. It also provided a **"big red button"**: if TE had problems, operators could disable it and fall back to shortest-path forwarding. 

This is a fantastic professor-question topic.

### If asked:

**"What happens if your centralized TE system fails?"**

Answer:

> **"B4 can disable the TE service and fall back to shortest-path forwarding. The authors describe this as a 'big red button' for fault recovery."** 

Remember that one. ⭐
